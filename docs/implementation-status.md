# 무엇까지 확인됐나요?

**실험실과 실제 Windows 앱 모두에서 Astra가 DeepSeek 자식에게 일을 맡기는 동작을 확인했습니다. Flash는 현재 `max` 고정이며, 같은 자식에게 추가 작업을 보내는 테스트에서도 max를 확인했습니다.**

기준일: 2026년 9월 12일, 한국 시간. 아래는 이 컴퓨터에서 수행한 실험 기록입니다. 문서 정리 과정에서는 모델을 다시 호출하지 않았습니다.

## 1. 지금 사용할 수 있는 기능

| 확인한 기능 | 결과 | 확인 근거 |
|---|---|---|
| 실험실에서 Astra가 기본 도구 사용 | 확인 완료 | 실제 파일 읽기 테스트 통과 |
| DeepSeek가 Codex 도구로 파일 읽기·쓰기 | 확인 완료 | 실제 DeepSeek API 응답과 결과 파일 확인 |
| Astra가 DeepSeek와 GPT에 나눠 맡기기 | 확인 완료 | 두 공급자·모델의 자식 세션과 생성 파일 확인 |
| 같은 DeepSeek 자식에게 추가 작업 전달 | 확인 완료 | 자식을 새로 만들지 않고 기존 자식이 후속 작업 수행 |
| Astra가 담당 모델을 자율 선택 | 확인 완료 | 준비된 간단한 두 작업에서 DeepSeek 자식 2개 선택. 다른 자유 작업에서는 GPT Luna 선택 |
| 실험실의 진행 상황 표시 | 확인 완료 | 작업이 끝나기 전에 메시지·도구 출력 표시, 실제 Astra 테스트로 확인 |
| 탐색기에서 실행 파일 더블클릭 | 확인 완료 | PowerShell 7이 검색 경로에 없는 조건으로 두 실행기 검사 |
| 별도 실험용 Windows 앱 시작 | 확인 완료 | 독립 앱이 패치된 작업 엔진을 실행하는 부모·자식 프로세스 확인 |
| 실제 Windows 앱의 혼합 작업 | 확인 완료 | 사용자 작업에서 DeepSeek 구현 → GPT 검토 → Astra 테스트 9개 통과 |
| Flash의 추론 수준 max 고정 | 확인 완료 | 설정 재생성 검사 및 실제 첫 작업·동일 자식 후속 작업 모두 max 확인 |

‘자율 선택 확인’은 Astra가 모델을 고를 수 있다는 뜻입니다. 작업별로 항상 같은 모델을 고르거나 최저 비용을 보장한다는 뜻은 아닙니다.

## 2. 사용자 Windows 앱 테스트: 누가 무엇을 했나요?

2026년 9월 12일 **17:06~17:08**, `C:\dev\example-workspace` 폴더에서 실행한 작업입니다. 총 약 **82초**가 걸렸습니다.

| 담당 | 실제 모델 | 한 일 |
|---|---|---|
| 총괄 | Astra | 일을 나누고 두 자식의 완료를 기다린 뒤 테스트 실행 |
| 구현 | DeepSeek Flash | 문자열을 정리하는 Python 함수와 테스트 파일 작성 |
| 검토 | Astra 자식 | 코드와 테스트를 읽어 검토. 지적 사항 없음 |

부모가 실행한 **테스트 9개가 모두 통과**했습니다. 모델의 자기 보고뿐 아니라 세션에 기록된 공급자·모델, 파일 수정 도구의 성공 기록, 실제 파일을 대조했습니다. [담당·시간·파일을 포함한 상세 보고서](test-results-20260912-1706.md).

**이 사용자 테스트는 max 고정 이전에 실행되어 Flash가 `low`로 기록됐습니다.** 이후 max 고정을 적용했고, **17:26에 시작한 별도 실제 혼합 테스트**에서 같은 Flash 자식의 첫 작업과 추가 작업이 모두 `max`인 것을 확인했습니다. 두 기록을 구분해서 보세요.

## 3. 아직 확인하지 않은 범위

| 항목 | 현재 상태 |
|---|---|
| 앱 종료 후 기존 DeepSeek 작업 재개 | 실제 DeepSeek로 프로세스를 완전히 재시작한 재개 테스트는 미실시 |
| 앱에서 보이는 모든 자식 상태·화면 표시 | 실제 작업은 세션·파일로 검증했으며, 모든 UI 상태를 화면에서 직접 확인한 것은 아님 |
| 장시간의 큰 프로젝트 작업 | 장시간 실사용 검증은 미실시 |
| Codex 전체 테스트 모음 | 관련 항목을 선별해 검사했으며 전체 모음은 미실시 |
| 앱 업데이트 후 계속 호환되는지 | 현재 설치본에서 확인. 업데이트 후 다시 확인 필요 |

진행 중인 대화의 엔진을 즉시 바꾸는 토글은 현재 구현 범위에 없습니다. 지금은 **원래 앱과 실험용 앱 중 사용할 창을 골라 여는 방식**입니다.

## 5. 수정한 문제와 코드 검사 기록

이하 내용은 문제 원인을 추적할 때 읽으면 됩니다. 소스 버전·파일 확인값·빌드 명령은 [개발자용 참고 문서](technical-reference.md)에 있습니다.

### 결과가 끝날 때까지 진행 과정이 안 보이던 문제

실험실이 자식 프로세스 종료까지 출력을 모아서 표시하던 방식을 바꿨습니다. 이제 C# 출력 수집기와 200ms UI 타이머로 실행 중에도 출력과 오류를 읽습니다.

검사용 프로세스가 줄바꿈 없는 한글 출력과 오류 출력을 내보내고 5초간 살아 있는 동안, 실험실은 첫 출력을 약 192ms 뒤 표시했습니다. 종료 직전 출력과 종료 코드도 보존했습니다. 근거 파일은 `work/manager-stream-observed.json`, `work/manager-stream-running.png`, `work/manager-smoke-stream.log`입니다. 이 파일들은 후속 검사에서 갱신될 수 있습니다.

Python 진행 표시 관련 검사 4개가 통과했고, 이전 사용자 실행의 이벤트 7,646개를 재생해 Astra·DeepSeek·Luna 표시도 점검했습니다. 이후 실제 Astra 기본 테스트로 실시간 표시를 확인했습니다.

### 더블클릭 시 pwsh.exe를 찾지 못하던 문제

두 `.cmd` 실행기가 Windows 기본 PowerShell의 절대 경로로 시작하도록 수정했습니다. 준비 스크립트가 PowerShell 7·Python/Pythonw·Git의 실제 경로를 찾아 실행할 프로세스에 전달합니다.

검색 경로를 `System32`만 남긴 조건에서 검사 2개가 통과했습니다. 두 실행기의 의존 프로그램 검색, 앱 읽기 전용 점검, 실험실의 실행 중 출력 표시를 확인했습니다. 탐색기와 같은 검색 경로로 일반 실험실 창도 열었습니다. 이 검사에는 모델 호출이 필요하지 않았습니다.

### Flash max 고정 검사

설정 재생성과 기존 앱 설정 보존을 확인하는 검사 2개가 통과했습니다. 실제 혼합 테스트 `20260912-172645-45e0bf`에서는 동일 Flash 자식의 두 턴 모두 max였습니다. Astra·Sol은 해당 테스트의 자체 설정인 low를 유지했습니다. 이 변경으로 런타임 실행 파일을 다시 빌드하지는 않았습니다.

### 런타임 코드 회귀 검사

관련 Rust 검사 657개를 선별해 실행했습니다. 첫 결과는 655개 통과, 2개 실패였고, 실행 과정에서 자동 재시도 후 통과한 항목 3개가 있었습니다. 외부 공급자 통합 검사 6개는 모두 통과했습니다.

시간에 민감한 에이전트 검사 4개를 작업자 4개로 다시 실행해 전부 통과했습니다. 높은 동시 실행 수에서 발생한 시간 초과였으며 런타임의 시간 제한을 늘리지는 않았습니다. 별도 공급자 검색 검사는 분리된 인증 환경과 모델 메타데이터에 맞게 테스트 자료를 수정한 뒤 통과했습니다.

- `just fix -p codex-core -p codex-agent-roles -p codex-model-provider -p codex-config`: 경고·추가 수정 없이 통과.
- `just write-config-schema`: 통과. 허용할 외부 공급자 설정 포함.
- `just fmt`, `git diff --check`: 통과. 무관한 포맷 변경은 내보낸 패치에서 제외.
- PowerShell·Python 스크립트 구문 검사: 통과.

기록은 `work/targeted-tests-first-run.log`, `work/regression-followup.log`, `work/provider-endpoint-test.log`에 있습니다. 이 결과를 Codex 전체 테스트 통과로 해석하면 안 됩니다.

### 가짜 외부 서버 검사의 첫 실패

`20260912-032117-5ea6b7`의 실패 기록은 그대로 보관합니다. 당시 판정기가 요청 옵션 문자열 `reasoning.encrypted_content`를 실제 암호화 입력으로 오인했고, 고정 응답 순서가 추가 확인 턴을 처리하지 못했습니다.

판정기를 실제 입력 데이터 필드 검사로 바꾸고 응답을 도구·작업 상태에 맞춰 수정한 뒤 후속 검사가 통과했습니다. 이 수정에는 런타임 변경이 필요하지 않았습니다. 통과한 검사에서는 기대한 외부 인증값이 전달됐고, 비어 있지 않은 OpenAI 암호화 입력과 OpenAI 계정 헤더가 외부 요청에 없음을 확인했습니다.
