# 수정 96: 공유 기록 안정성 — 순번 중복, 느린 삭제, 하위 에이전트, 완전 종료

수정 96에서 함께 고친 공유 기록 관련 문제들입니다. 전환 캐시 최적화는
[switch-cache-optimization-96](switch-cache-optimization-96.md)에 따로 정리했습니다.

## 1. 작업이 열리지 않던 문제: 기록 순번 중복

### 증상
큰 작업 하나를 열면 `thread history projection for <id> expected ordinal N, got N-1` 오류가 났습니다.
사이드바의 목록 항목은 그대로 보였습니다.

### 원인
- 기록 파일(JSONL)의 각 줄에는 순번(`ordinal`)이 있고, 페이지 색인은 순번이 1씩 늘어난다고 가정합니다.
- 기록기가 턴 시작 때 파일 끝에서 마지막 순번을 찾을 때, 마지막 줄을 형식대로 해석하지 못하면 그 줄을
  건너뛰었습니다(`rollout/src/ordinal.rs`). 그러면 건너뛴 줄의 순번을 다음 줄에 다시 붙입니다.
- 해석에 실패한 이유: 워크스페이스 전체 빌드에서 `serde_json`의 `arbitrary_precision`이 켜지면, 사용량 줄
  (`token_count`)의 소수 값이 형식 해석(flatten)을 통과하지 못합니다. 런타임의 일반 읽기 경로는 이 문제를
  우회하지만, 순번 찾기 경로는 우회하지 않았습니다.
- 실제 저장소 전체(3천여 작업)를 검사한 결과 이런 작업은 하나였고, 중복은 두 군데였습니다.

### 복구
- `scripts/repair_history_ordinals.py`: 기본은 미리보기, `--apply`로 적용, `--scan`은 저장소 전체 검사.
- 첫 중복 뒤 줄의 순번 숫자만 위치에 맞게 다시 매깁니다. 내용은 바꾸지 않습니다.
- 적용 전 원본 전체를 `work/history-recovery/ordinals-<시각>-<id>/`에 백업하고, 파일을 연 프로세스가 있거나
  다른 작업이 이 작업의 순번을 참조하면 거절합니다.
- 복구 후 처음 열 때 색인을 파일 처음부터 다시 만드므로 큰 작업은 1분 이상 걸릴 수 있습니다.

### 방지 (런타임)
- 모든 기록기가 `final_durable_ordinal()` 하나로 마지막 순번을 찾습니다. 줄 내용은 해석하지 않고 최상위
  `ordinal` 필드만 읽으므로, 새 이벤트 형식이나 해석할 수 없는 내용도 순번을 지킵니다.
- 끝이 잘린 줄(비정상 종료)은 이전처럼 건너뛰고 같은 순번으로 다시 씁니다. 공유 기록에서는 잘린 줄 뒤에
  줄바꿈을 먼저 넣어 새 줄이 붙어 버리지 않게 합니다.
- 완전한 줄인데 순번을 읽을 수 없으면 추측하지 않고 쓰기를 거절합니다.
- 색인 오류 메시지에 복구 도구 사용법을 덧붙였습니다.

## 2. 작업 삭제가 수십 초 걸리던 문제

- 삭제는 다른 작업이 이 작업에서 갈라져 나왔는지 확인하려고 모든 기록 파일의 머리 줄을 읽습니다.
- 공유 저장소 경로가 삭제를 작업마다 따로 처리해서, 삭제 대상과 그 하위 에이전트 작업 수만큼 저장소 전체를
  반복해 훑었습니다(실측 46–80초). 그동안 같은 런타임의 작업 열기도 기다렸습니다.
- 이제 한 번의 삭제 요청은 한 번만 훑고, 삭제 대상보다 나중에 만들어졌을 수 있는 파일만 읽으며(파일 이름과
  UUIDv7 시각 기준, 시계 오차를 위해 7일 여유), 머리 줄을 병렬로 읽습니다. 시각을 알 수 없으면 전체를 훑습니다.

## 3. 하위 에이전트가 있는 작업의 전송 실패

- 다른 프로필이 공유 작업을 갱신한 뒤 메시지를 보내면, 런타임은 작업을 닫고 최신 기록으로 다시 엽니다.
  하위 에이전트가 로드돼 있으면 부모를 닫을 수 없어 `a descendant actor is still loaded`로 실패했습니다.
- 이제 쉬고 있는 하위 에이전트를 깊은 것부터 먼저 닫고 부모를 다시 엽니다. 닫힌 하위 에이전트는 다음에 쓸 때
  기록 그대로 다시 열립니다. 부모에게 온 하위 에이전트 완료 알림과 하위 에이전트에 쌓인 메시지는 잃지 않고
  옮깁니다.
- 하위 에이전트가 실제로 일하는 중이면 아무것도 보내지 않고 "끝난 뒤 다시 보내 주세요"라고 알립니다.
- SSH 프로젝트는 서버의 원격 런타임이 이 수정을 포함한 버전으로 바뀌어야 적용됩니다.

## 4. 완전 종료가 대기 중인 SSH 설정 적용에 막히던 문제

[profile-remote-drain-89](profile-remote-drain-89.md)의 추가 절에 정리했습니다. 완전 종료가 오면 대기 중인
"작업이 끝나면 다시 열기" 예약을 "작업이 끝나면 종료"로 바꿔 받아들입니다.

## 5. 작업 메모 창 열림 상태

작업 메모 창의 열림/닫힘을 프로필마다 저장합니다(`work/control-center/notes-panel.json`). 프로필을 바꾸거나
다시 실행하면 그 프로필의 상태를 되살립니다. 창 너비는 공통입니다.

## 확인하지 못한 것

- 실제 앱에서의 동작은 수정 96 적용 후 확인합니다. 위 내용은 오프라인 시험과 복사본 검증 결과입니다.
- 순번 복구는 실제 저장소의 한 작업에 적용했고, 사본 검증에서 133개 턴이 모두 열리는 것을 확인했습니다.
