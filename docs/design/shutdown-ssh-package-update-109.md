# 수정 109 — SSH 종료 대기, 완전 종료, 공식 패키지 업데이트

## 확인한 원인

수정 108 실행 로그에서 로컬 프로필 종료 후 원격 종료 예약이 남았고, 이전 서비스는
이 예약까지 현재 실행 중인 로컬 작업으로 취급했다. 관리창의 종료 요청을 거절하는 동안
다음 실행은 같은 원격 종료 예약을 이어받았다. 한 서버에서 종료 중인 프로필 프로세스가
남아 있어 같은 프로필의 다른 SSH 서버 연결도 유지보수 잠금에 막혔다.

문제가 난 서버의 기존 프로세스들은 수일 전 실행된 바이너리였다. 종료 신호를 받은 뒤
리스너를 닫았지만 프로세스와 인스턴스 잠금이 남았다. 한 프로필에서는 진행 중 답변과
연결이 모두 0이라는 종료 로그를 확인했다. 나머지는 작업 파일과 데이터베이스를 닫고
런타임 내부 이벤트 처리용 FD만 유지했으며 자식 프로세스도 없었다. 정확히 어느 함수에서
옛 바이너리가 멈췄는지는 스택을 확보하지 못했으므로 확정하지 않는다.

별개로 기존 공식 앱 업데이트는 Windows 패키지 설치와 관리용 앱 교체를 한 절차로 묶었다.
독립 사본으로 실행 중인 작업까지 종료·SSH 유휴 확인·새 UI 호환성 검사를 요구해 패키지
설치가 불필요하게 차단됐다. 공통 기록 저장소를 사용하는 현재 런타임에는 기존
`thread/managedIdleStatus`가 거절되는 문제도 있다. 이 거절을 유휴 상태로 바꾸지는 않는다.

## 변경

- `manager/service/src/main.rs`: 명시적 완전 종료에서만 저장된 SSH 백그라운드 대기 예약을
  실행 중 로컬 작업과 구분한다. 실행 중 관리 명령, 열린 프로필, 다른 클라이언트, 새 실행은
  계속 차단한다. 자동 서비스 교체의 조건은 완화하지 않는다.
- `manager/Shell/WorkspaceShutdown.cs`: 새 서비스의 `shutdown_remote_journals` 기능을 확인한다.
  이전 서비스에는 로컬 종료·실행 차단·단일 클라이언트·대기 예약만 존재함을 확인한 뒤
  기존 EOF 종료 경로를 사용한다. 원격 프로세스 종료 성공을 꾸며내지 않는다.
- `scripts/manager_core/managed_package_update.py`, `updates.py`, `update_jobs.py`:
  검증된 독립 관리용 사본으로 실행 중이면 `official_package_only` 설치를 선택한다.
  공식 설치본을 실제로 실행 중인 프로세스가 있거나 독립 사본을 검증할 수 없으면 차단한다.
  다운로드 서명과 패키지 신원, 설치 직전 상태, 설치 후 버전, 관리용 사본 보존을 확인한다.
  이 경로는 프로필·SSH를 종료하거나 다시 시작하지 않는다. 알 수 없는 설치 결과를
  무작정 재실행하지 않고 재확인한다.
- 실제 설치 시험에서 PowerShell 7의 `PSModulePath`를 Windows PowerShell 5에
  물려주어 서명 검사 모듈을 불러오지 못하는 추가 원인을 확인했다. 자식 셸이 자체
  기본 모듈 경로를 사용하게 하고, 최초 MSIX 인증서 검사에는 120초를 허용한다.
  서명을 생략하지 않으며 원본 프로세스의 환경 변수는 변경하지 않는다.

공식 Windows 패키지 버전과 현재 관리용 UI 버전은 별개다. 패키지 설치가 끝났어도
새 관리용 화면의 호환성을 검증하기 전까지 기존 관리용 사본을 사용한다.

실제 Windows 설치 시험에서는 파일 경로가 독립 사본이고 프로세스의 패키지 토큰과
ApplicationUserModelId가 모두 없더라도 AppX 배포 서비스가 기존 앱을 사용 중으로
판단했다(`0x80073D02`). 따라서 경로와 프로세스 토큰만으로 즉시 교체 가능하다고
단정하면 안 된다. 공식 지연 등록 기능을 사용하는 경우에도 다운로드/준비/적용 대기와
실제 설치 버전 확인을 구분해야 한다.

`install_worker.py`는 공식 `-DeferRegistrationWhenPackagesAreInUse` 옵션을 지원하고,
완료 응답 후 설치 버전이 이전 값이면 `registration_pending`으로 기록한다. 이는
원본 Codex가 다음 실행될 때 적용되는 Windows 기능이다. 관리창만 다시 여는 것과
원본 패키지 실행을 같은 것으로 취급하지 않는다. 대기 중에는 설치를 반복하지 않고
등록 버전을 재확인하며, 목표 버전이 확인되어야 `complete`로 바꾼다.

새 설치 영수증에는 Windows의 확정적인 사용 중 거절을 별도로 기록한다. 예전 영수증의
일반적인 실패는 같은 시간대·패키지의 다른 Windows 이벤트만으로 성공/실패가 확정됐다고
판정하지 않는다. 현장 첫 실패의 복구는 별도 백업 및 해당 요청의 배포 로그 대조를 거쳐
수행했다. 복구 후에는 같은 작업 ID라도 최신 트랜잭션 결과를 표시해야 한다.

## 현장 복구와 검증

실제 비밀값, 계정 식별자, 서버 경로는 공개 문서에 기록하지 않는다. 로컬 검증 결과와
현장 복구 기록은 Git 밖 `work/validation/*-109/`에 둔다.

- 멈춘 기존 원격 프로세스 6개의 부팅 ID, PID 시작 시간, 실행 파일 해시, 프로필,
  종료 요청, 소켓, 파일, 자식 프로세스를 확인했다. 일관된 SQLite 백업과 관련 기록을
  보존한 뒤 이 6개만 정리했다. 모두 프로세스 소멸과 잠금 해제를 확인했다.
- 현재 Windows 작업 프로세스는 이 정리 대상에 포함하지 않았다.
- 종료 관련 Rust 검사 6개, WPF 종료 자체 검사 15개, .NET 빌드가 통과했다.
  서비스 전체 63개 검사에서는 부하 중 응답 시간 상한 검사 1개가 실패했고,
  해당 검사를 단독 실행했을 때 통과했다. 62개는 전체 실행에서 통과했다.
- 공식 패키지 분리 관련 Python 검사 133개와 PowerShell 환경 수정 후 관련 검사
  73개가 통과했다. 두 실행에는 겹치는 검사가 있으므로 합산하지 않는다.
- 실제 SSH 재연결, 실제 Windows 패키지 설치, 최종 고정 배포본 검증 결과는 아래에
  후속 기록한다. 소스 검사 통과만으로 현장 복구 완료를 의미하지 않는다.

중간 고정 후보 `20261004-052819-013`의 Python 검사 73개, WPF 종료 검사 15개,
파일 해시 218개는 통과했다. 이 후보 이후 발견한 AppX 사용 중 거절 처리까지 최종
후보에 포함해야 하므로 이 중간 후보는 사용자 기본 실행 대상으로 게시하지 않았다.

## 최종 현장 상태

- 최종 관리창은 수정 109, 빌드 `20261004-053808-002`로 교체했다. 이전 관리창의 정상
  창 종료 경로를 사용했고, 새 창이 기존 프로세스에 다시 연결되는 것을 로그로 확인했다.
  실행 중 백엔드는 작업을 보존하기 위해 그대로 유지했다. 새 관리창에는 이전 서비스에서도
  사용할 수 있는 완전 종료 보완이 포함된다. 새 서비스 자체는 다음 완전 종료 후 적용된다.
- 최종 고정 Python 코드의 검사 89개, 파일 해시 218개, 고정 경로에서 가져온 모듈 61개를
  검증했다. 종료 자체 검사 15개를 통과한 네이티브 빌드 17개 파일과 동일함을 확인했다.
- 실제 공식 업데이트 요청은 Windows의 지연 등록으로 정상 준비됐다. 목표는
  `26.930.3930.0`, 조사 시 등록된 버전은 `26.930.2377.0`이다. 결과는
  `registration_pending`이며 **설치 버전이 이미 바뀐 것으로 보고하지 않는다**.
  관리용 화면은 계속 검증된 `26.917.9434.0`을 사용한다.
- 이전 관리 서비스의 종료된 업데이트 작업 캐시도 잠금 및 설치기 종료 증거를 확인한 뒤
  현재 대기 결과로 맞췄다. 설치 기록과 영수증의 해시는 유지했으며 설치를 반복하지 않았다.
- SSH 공통 차단은 해제됐고 7개 프로필의 서버 3곳, 총 21개 연결에서 계정·실행 세대·호스트
  결합과 작업 목록 조회를 확인했다. 한 프로필은 로컬 UI가 응답하지 않아 작업·도구·승인·
  대기열이 모두 비었음을 확인한 뒤 그 프로필만 복구 재실행했다. 다른 9개 프로필은
  프로세스와 실행 세대를 유지했다. 재실행 후에도 ChatGPT 화면이 유지된 이 프로필은,
  해당 프로필로 범위를 고정한 기존 native `codex://threads/new?mode=codex` 요청 후
  세 서버 연결을 복구했다. 모드 저장 파일을 추측해서 변경하거나 계정의 접근 조건을
  우회하지 않았다. 그 뒤 기존 작업 열기 요청은 수신됐지만, 실제 화면 선택을 관찰하는
  기록은 갱신되지 않아 작업 화면 이동 완료까지 검증한 것은 아니다.
- 실행 중인 다른 작업을 중단하지 않기 위해 실제 전체 프로필 종료는 다시 수행하지 않았다.
  전체 종료의 확인 범위는 서비스 통합 검사, 관리창 종료 검사, 이전 실행 로그 대조다.

## Rust 종료 경로 보강

`runtime/codex-rs/app-server/src/lib.rs`의 두 watch 수신 경로에서 송신자 종료 후
즉시 오류가 반복되는 분기를 비활성화한다. 작업 수 관찰이 끊긴 상태를 0개로
간주하지 않으므로, 상태를 알 수 없다는 이유만으로 실행 중 작업을 종료하지 않는다.
`otel_reloader.rs`는 exporter 종료에 상한을 둔 기존 API를 사용한다. 이는 코드에서
확인한 결함의 보강이며, 과거 서버 프로세스 정체가 반드시 이 원인이라는 뜻은 아니다.

누적 패치는 기존 변경을 보존한 채 이 두 파일과 `otel_reloader_tests.rs`만 추가로
반영했다. 기존 기준 커밋은 유지하며 결과 트리는
`32eae5e0e96daf19670367fc7159eef18f2ff50c`이다. 새 Windows 및 Linux 작업 폴더에서
같은 트리로 복원함을 확인했다. OTel crate 검사 4개, 실제 변경 소스를 추출해 컴파일한
watch 검사 3개(Windows/Linux), exporter 정체 검사(Linux)를 통과했다. app-server
crate 전체 빌드는 완료하지 않았으며 새 원격 바이너리는 배포하지 않았다.

## 남은 경계

이전 원격 바이너리의 모든 종료 정체를 자동 강제 종료하는 기능은 추가하지 않는다.
실행 중 답변 상태를 알 수 없으면 종료 성공이나 유휴 상태로 처리하지 않는다.
기존 공통 기록용 런타임의 유휴 조회 지원은 별도 개선 대상이며, 공식 패키지 설치는
독립 사본의 검증으로 이 조회에 의존하지 않게 한다.
