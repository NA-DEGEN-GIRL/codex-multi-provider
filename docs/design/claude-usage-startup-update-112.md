# 수정 112 — Claude 사용량, 시작 시 업데이트 대기, 긴 대화 전환

## 확인한 원인

- Claude 사용량은 공식 CLI의 대화형 `/usage` 화면을 숨겨서 읽었다. 프로필별 CLI의 첫 실행 설정이 끝나지 않으면 테마 선택 화면에서 멈춰, 로그인된 계정도 사용량을 가져오지 못했다.
- 공식 Windows 패키지 등록은 완전 종료 뒤에도 수십 초 걸린다. 등록 도우미가 실행되는 동안 작업 공간을 다시 열면 새 Codex 프로세스가 먼저 시작되어 Windows가 `0x80073D02`(사용 중인 패키지)로 등록을 거절했다. 설치 파일 다운로드 실패와 구별된다.
- 배포된 Linux Claude 런타임의 해시가 원격 안전 종료 검증 목록에서 빠져 있었다. 종료 요청 뒤 확인 대기가 남은 프로필은 다음 연결도 보류했다.
- 긴 기존 대화를 Claude로 전환할 때 전체 기록을 반복해서 해시하고, 압축 요약이 이미 대신하는 이미지까지 디코딩·저장했다. 대화 읽기 또한 완료 턴마다 이전 항목 전체를 다시 순회했다. 실제 오류 대화의 계보는 약 1.6 GB였고, 취소 직전 이미지 147개가 준비됐지만 Claude 추론은 시작되지 않았다.

## 변경 경로

- `scripts/manager_core/claude_usage_api.py`: 선택된 계정의 단기 접근 토큰으로 고정된 공식 사용량 주소를 조회한다. 리디렉션을 허용하지 않고 5시간·주간 비율과 초기화 시각만 보관한다. 토큰 갱신·추론 호출은 하지 않는다. `claude_usage.py`는 조회 전후 계정 일치를 확인한다. 누락·오류를 0% 사용으로 표시하지 않는다.
- `scripts/finish_package_update.py`와 `manager/Shell/PackageUpdateAfterExit.cs`: 보류된 등록이 있으면 새 관리창의 프로필 실행 전에 기존 설치 도우미와 같은 잠금을 기다린다. 이미 다른 도우미가 시도한 경우 결과만 확인한다. 설치 종료가 불명확하면 새 프로필을 시작하지 않는다. `App.xaml.cs`가 진행 창의 수명을 관리한다.
- `scripts/remote_helpers/native_controller.py`: 격리 시험으로 두 번의 SIGHUP에도 실행 중 작업을 보존하고 완료 뒤 종료하는 것을 확인한 Linux 바이너리의 SHA256을 등록했다. 버전 문자열만으로 다른 바이너리를 허용하지 않는다.
- `scripts/manager_core/ssh_connection_wait.py`: 설정 준비 대기의 조회 간격을 0.1초에서 최대 1초까지 늘려 동시 프로필의 상태 조회 집중을 줄였다. 준비 완료·실패 판단 및 전체 대기 제한은 유지한다.
- `runtime/codex-rs/core/src/tasks/claude_code/`: 전체 기록의 스냅샷 검증과 실제로 전달할 문맥을 구분한다. 전달 문맥을 고른 뒤 선택된 첨부만 파일로 준비하며, 잘린 내부 참조를 모델에 전송하지 않는다. 오래 걸리는 기록 읽기에는 준비 중 안내를 보낸다.
- `runtime/codex-rs/core/src/portable_context/agent_summary.rs`: 확인할 외부 에이전트 요약이 없는 대화는 요약 검증용 전체 해시를 계산하지 않는다. 기존의 계정별 재개·편집 감지용 스냅샷은 유지한다.
- `runtime/codex-rs/rollout/src/model_transcript.rs`: 완료 턴 집합을 기록하고 최종 결과를 만들 때 완료 상태를 반영한다. 동시 진행 중 턴과 ID 없는 과거 중단 이벤트를 구분한다.
- `runtime/codex-rs/rollout/src/compression.rs`: 전체 순회용 읽기 버퍼를 8 KiB에서 256 KiB로 늘려 작은 비동기 파일 읽기의 반복을 줄인다. 목록 조회용 헤더 읽기의 작은 버퍼는 유지한다.

## 검증 및 적용 경계

- 세 Claude 프로필의 실제 5시간·주간 사용량 조회와 상태 저장을 확인했다. 첫 실행 설정이나 모델 호출을 요구하지 않았다.
- 세 Claude 프로필의 로컬 및 SSH 서버 세 곳에서 연결·인증·열린 작업 목록 조회를 확인했다. 원격 카탈로그에서 고른 실제 대화 표본의 메타데이터 읽기(`thread/read`, `includeTurns=false`)도 12개 조합에서 성공했다. 원격 종료 대기에 갇힌 두 프로필은 정상 종료 절차와 재연결로 복구했다.
- 관리 앱의 사용량·업데이트·SSH 관련 집중 검사 60개를 통과했다. 최종 관리 앱 후보 `20261004-094745-143`의 고정 Python 검사 290개 중 286개 통과·환경상 제외 4개이며 221개 파일 해시를 검증했다. Claude 프로필·원격 업데이트·배치·창 제어 WPF 자체 검사 4종도 통과했고, 최종 사본과 시험한 관리창 DLL의 SHA256이 동일하다.
- 별도 실행 엔진의 네이티브 검증과 적용 상태는 관리 앱 후보의 합격 여부와 구분한다.
- Windows 엔진 후보 `20261004-102538-d47321`은 빌드됐으며, 같은 바이너리의 공통 기록 편집 15개 항목과 4개 클라이언트의 정본 저장소 16개 항목을 통과했다. 실제 모델 호출은 없었다. 증거는 `artifacts/results/shared-editing-55ae7a3e/report.json`, `artifacts/results/canonical-store-d4b7a135/report.json`이며 엔진 SHA256은 `62a3dc9b697fa02821d3c36782c58321044bb6373e04bc4eff1ea0cca7260bb7`이다.
- 같은 후보에 포함된 app-server로 `tests/test_manager_claude_runtime_e2e.py`의 11개 검사를 통과했다. GPT→Claude→GPT, Claude 계정 A→B→A, 모델·effort 변경, 정확한 이미지 파일 전달, 중단·승인·계획 모드, 압축 요약의 계정 간 전달을 가짜 CLI·응답 서버로 검사했다. 실제 유료 모델 호출이나 사용자 대화 변경은 하지 않았다.
- `just test -p codex-rollout --lib model_transcript`의 완료·중단·동시 턴 귀속 검사 3개를 통과했다. 나머지 140개는 이 필터의 실행 대상이 아니며, 전체 Rust 작업 공간 시험을 통과한 것으로 주장하지 않는다.
- `just test -p codex-core --lib -E 'test(tasks::claude_code) | test(portable_context)'`로 Claude 문맥·첨부·위임·메시지 처리 및 호환 문맥 검사 31개를 모두 통과했다. 실행 대상 밖의 2,426개는 제외됐다. 첫 시도에서 새 이미지 테스트의 직렬화 대상 두 곳에 컴파일 오류가 있었고, 실제 응답 항목을 직렬화하도록 고친 뒤 재실행한 결과다.
- 최종 소스 패치를 새 작업 폴더에 복원하여 `70c3d60c8a8bb97a94338d389c568b8f71ed4d8e` 트리와 일치함을 확인했다. 엔진 빌드 이후 소스 차이는 이미지 단위 테스트의 직렬화 대상을 고친 두 줄뿐이며, 실행용 코드는 동일하다.
- 긴 대화 처리 성능을 측정한 새 네이티브 빌드는 Windows용이다. Linux 원격 엔진을 새로 빌드해 교체한 것으로 해석하지 않는다. SSH 연결 복구와 안전 종료 검증 목록 수정은 별도의 관리 기능 변경이다.
- 실제 긴 대화 계보를 읽는 별도 프로그램에서 전체 순회 시간이 약 566초에서 166초로 줄었다. 바뀌지 않은 첫 번째 파일은 약 345초에서 84초로 줄었다. 전체 결과 항목은 38,208개에서 38,454개로 늘었는데 검사 중 현재 대화에 새 기록이 추가되었으므로, 두 전체 결과를 동일한 스냅샷으로 간주하지 않는다. 이 측정은 기록 읽기·해석만 포함하며 Claude 응답 시간이나 UI 전체 전환 시간을 뜻하지 않는다.
- 개인별 경로·계정·서버·로그 증거는 Git 밖 `work/validation/release-112/`에 둔다. 문서에는 자격증명이나 대화 본문을 포함하지 않는다.
- 원본 대화와 압축 기록은 수정하지 않는다. 관리 앱 후보를 빌드하는 것과 실행 중 서비스/네이티브 프로세스 교체는 별개다. 실행 중인 다른 작업을 강제 종료하지 않는다.
- 사용량 자동 갱신과 SSH 종료 검증은 고정 Python 관리 서비스가 담당한다. 창만 닫았다 여는 것으로 기존 서비스가 바뀌지는 않는다. 실행 중 작업을 마친 뒤 완전 종료하고 새 릴리스로 시작해야 새 코드가 지속 적용된다.
- 관리 앱 `20261004-094745-143`과 Windows 엔진 `20261004-102538-d47321`을 다음 실행용 포인터에 등록했다. 기존 실행 프로세스는 재시작하지 않았다. 이전 관리 앱 포인터는 `work/validation/release-112/manager-previous.json`, 이전 엔진 포인터는 `artifacts/manager-runtime/previous.json`에 보존했다.
- 실제 Windows 패키지 등록 완료와 사용자가 보는 전체 대화 전환의 수동 합격을 빌드 성공만으로 주장하지 않는다.

## 사용 중인 설치에 적용하기

1. 진행 중인 작업을 마친 뒤 작업 공간 앱에서 **완전 종료**한다. 창만 닫으면 이전 관리 서비스가 남는다.
2. 작업 공간 앱을 다시 실행한다. 보류된 공식 앱 업데이트가 있으면 새 프로필을 열기 전에 등록 진행 창이 표시된다. 진행 창의 결과를 기다린다.
3. 관리 앱의 수정 번호가 **112**인지 확인한다. Claude 프로필의 사용량을 갱신하여 5시간·주간 잔여량과 초기화 시각을 확인한다.
4. 기존 SSH 프로젝트와 GPT에서 시작한 대화를 Claude로 열어 확인한다. 큰 대화는 기록 준비 안내가 먼저 나올 수 있다. 문제가 남으면 이때의 프로필·수정 번호·진행 기록을 함께 확인한다.
