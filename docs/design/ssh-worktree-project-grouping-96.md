# 수정 96 — SSH worktree 프로젝트의 대화가 상위 저장소 프로젝트로 옮겨지는 문제

## 증상

SSH 호스트(`<ssh-host>`)에 git worktree 프로젝트와 그 상위 저장소 프로젝트를 함께 등록한 경우다.
일부 프로필에서 worktree 프로젝트의 대화를 하나 선택하면, 그 프로젝트의 대화가 모두
상위 저장소 프로젝트 아래로 옮겨졌다. worktree 프로젝트에는 `채팅 없음`이 표시됐다.

- 앱을 다시 시작하면 원래대로 돌아온다.
- 같은 대화라도 어떤 프로필에서는 증상이 나타나고 어떤 프로필에서는 나타나지 않았다.
- 제공자(DeepSeek, ChatGPT), 로그인, 관리자 동기화와는 관계없다.
- 대화 기록과 카탈로그 DB는 바뀌지 않는다. 사이드바 표시에만 생기는 문제다.

## 원인

Codex 26.917 렌더러의 사이드바 분류 코드(번들의 `DXr`)에서 생긴다.

1. 두 프로젝트는 심볼릭 링크 경로(`/home/<user>/projects/...`)로 등록되어 있다.
   대화의 작업 폴더(cwd)는 실제 경로(`/srv/...`)로 기록된다.
   worktree 폴더는 상위 저장소와 같은 git common dir을 쓰는 linked worktree다.
2. 앱을 시작하면 대화는 올바른 곳에 들어간다. 정확한 경로 비교와 호스트의 `pwd -P`
   정규 경로 표로 대화의 cwd를 worktree 프로젝트에 맞추기 때문이다.
3. 대화를 선택하면 그 대화는 요약이 없는 실행 중 항목이 된다. 앱은 이런 항목의 cwd로
   git 정보를 조회한다. 결과는 폴더 단위로 저장되므로 그 폴더의 대화 전체에 적용된다.
4. 조회 결과 cwd가 linked worktree로 확인되면 앱은 대화를 "같은 저장소의 프로젝트"로
   다시 배치한다(`vXr`). 이때 등록 경로(심볼릭 링크)와 git이 알려 준 실제 경로를 비교하므로
   정확히 맞는 프로젝트를 찾지 못한다.
5. 그러면 같은 common dir을 쓰는 프로젝트 중 **그 프로필의 사이드바 순서에서 첫 번째**
   프로젝트를 고른다. 상위 저장소 프로젝트가 위에 있는 프로필에서만 대화가 옮겨졌다.
   사이드바 순서는 프로필마다 따로 저장된다. 그래서 프로필마다 결과가 달랐다.

로컬 프로젝트에는 "cwd가 등록된 프로젝트 루트면 다시 배치하지 않는다"는 보호(`uXr`)가
원래 있다. SSH 프로젝트에는 같은 보호가 없었다.

## 수정

`scripts/manager_core/original_sync_bundle.py`에 `renderer_remote_root_patches()`를 추가했다.
관리용 데스크톱 복사본(`desktop_bundle.py`)과 원본 동기화 복사본 모두 렌더러를 만들 때
이 패치를 적용한다.

- SSH 대화의 cwd가 그 호스트에 등록된 프로젝트 루트와 같으면 다시 배치를 건너뛴다.
  경로가 정확히 같거나, 호스트의 정규 경로 표에서 같은 경로일 때가 해당한다.
  그 프로젝트가 대화를 그대로 가진다.
- 비교는 대화가 속한 호스트의 프로젝트끼리만 한다. 다른 호스트에 같은 경로가 등록되어
  있어도 영향을 받지 않는다.
- 로컬 대화는 바뀌지 않는다.
- 등록된 루트가 아닌 SSH cwd는 이 보호의 대상이 아니다. `~/.codex/worktrees/...`, 하위 폴더,
  정규 경로 표가 아직 없는 경우(호스트 연결 전)가 여기에 속한다.
- 그래서 정규 경로 표가 없는 동안에는 이 보호가 아무것도 하지 않는다. 보호만 있던 때에는
  cwd 조회가 먼저 끝나면 증상이 잠깐 나타날 수 있었다. 수정 119의 순서 정렬(아래)이 들어간 뒤에는
  이 구간에도 worktree 프로젝트에 남는다. 위 경우들의 후보 순서도 순서 정렬이 정한다.
- 26.917 렌더러에서 확인한 함수 전체가 정확히 한 번 있을 때만 패치한다.
  - 없으면 패치하지 않는다. 앱은 원래 동작으로 실행된다.
  - 두 번 이상 있으면 오류로 멈춘다.
  - 이미 패치된 번들에는 다시 적용하지 않는다.
- 26.915에도 같은 동작이 있지만 코드 모양이 달라 이번 패치 대상이 아니다.
  관리자가 26.915 복사본으로 실행하면 증상은 그대로 남는다.
- Codex가 새 버전으로 바뀌어 함수 모양이 달라지면 패치는 조용히 빠진다(원래 동작).
  번들 확인 검사는 26.917 복사본만 본다. 새 버전에서는 이름을 확인해
  `_REMOTE_ROOT_VARIANTS`에 변형을 추가해야 한다.
  26.930.4958에서 실제로 이렇게 빠졌다. 26.930은 이제 조용히 빠지지 않는다(아래 26.930.4958 절).

패치 파일이 바뀌면 관리용 데스크톱 복사본의 키도 바뀐다. 관리자를 다시 빌드한 뒤
프로필을 새로 실행하면 새 복사본이 만들어지면서 적용된다. 이미 실행 중인 프로필 창은
다시 시작해야 반영된다.

- 패치 선택: 함수가 한 번 있으면 패치 하나를 만든다. 없거나 모양이 바뀌면 패치하지 않는다.
  두 번 있으면 거부한다. 이미 패치된 번들에는 다시 적용하지 않는다.

  - 패치 전: 상위 저장소가 위에 있고 cwd 조회가 끝나면 대화가 옮겨진다(증상 재현).
    순서가 반대면 옮겨지지 않는다.
  - 패치 후: 순서와 조회 여부에 관계없이 worktree 프로젝트에 남는다.
  - 원래와 같아야 하는 경우는 패치 전후 결과가 같다. 원격 Codex worktree, 원격 하위 폴더,
    정규 경로 표 없음, 실제 경로로 등록한 프로젝트, 로컬 루트, 로컬 worktree, 로컬 하위 폴더가 해당한다.
    다른 호스트의 대화도 포함한다. 그 cwd가 첫 호스트에 등록된 프로젝트의 정규 경로와 같아도
    원래대로 배치된다.
- 번들 확인: 이 컴퓨터에 관리용 26.917 복사본이 있으면 대상 함수와 보조 함수가 번들과
  정확히 같은지 확인한다.

## 26.930.4958 — 열지 않은 worktree 대화가 보이지 않는 문제 (수정 119)

26.930.3930도 같은 코드다(이름만 다르다). 아래 내용은 두 빌드에 모두 해당한다.

### 증상

SSH 호스트에 저장소 프로젝트를 등록하고, 같은 git common dir을 쓰는 linked worktree 폴더는
프로젝트로 등록하지 않은 경우다. 그 worktree 폴더의 대화가 사이드바에 보이지 않았다.
그 창에서 대화를 하나 열면 그 폴더의 대화가 저장소 프로젝트 아래에 나타났다.
창마다 연 대화가 달라서 프로필마다 보이는 대화가 달랐다.

### 원인

1. 사이드바는 대화 폴더(cwd)의 git 정보를 조회한다. 조회할 폴더를 고르는 함수(번들의 `gIn`,
   26.917의 `pXr`)는 요약이 있는 항목, 즉 창에 로드되지 않은 대화를 건너뛴다.
   Codex worktree(`~/.codex/worktrees/...`) 안의 대화만 예외다.
2. 분류 함수(`AIn`)는 SSH 대화의 cwd가 등록된 프로젝트 루트가 아니면 git 정보로만
   저장소 프로젝트를 찾는다(같은 common dir 재배치). git 정보가 없으면 그 대화를 버린다(`if(p)return`).
3. 그래서 로드된 대화가 있는 폴더만 조회됐고, 나머지 worktree 대화는 표시되지 않았다.
4. 4958에서 분류 함수의 이름이 바뀌어 `_REMOTE_ROOT_VARIANTS`에 맞는 변형이 없었다.
   수정 96 보호가 조용히 빠져 있었고, 등록된 worktree 프로젝트의 대화를 열면 수정 96 증상도
   다시 생길 수 있었다.

### 수정

- `_REMOTE_ROOT_VARIANTS`에 4958 이름(`yFn`, `yIn`, `DIn`, `vIn`, `Yu`, `bIn`, `xIn`, `_Fn`, `mIn`)을
  추가했다. 실제 4958 렌더러(app-initial)에서 `_remote_root_section`이 한 번만 맞는 것을 확인했다.
- `renderer_summary_dir_patches()`를 추가했다. 폴더 선택 함수에서 요약 항목을 건너뛰는 조건을
  로컬 대화에만 적용한다(`n.summary!=null&&e===t&&!Yu(...)`; `e`는 대화의 호스트, `t`는 로컬 호스트).
  SSH 대화는 요약만 있어도 cwd를 조회한다.
  - 로컬 대화는 그대로다.
  - 프로젝트에 직접 지정된 대화, 프로젝트 없음으로 고정된 대화, `projectless` 대화, `~` 폴더 대화,
    연결된 원격 프로젝트가 없는 호스트의 대화는 기존 조건대로 조회하지 않는다.
  - 이름 표 `_SUMMARY_DIR_VARIANTS`에는 4958(`Fi`, `Yu`), 3930(`Pc`, `Ch`), 26.917(`zs`, `R`)이 있다.
    대화 한 줄 처리 전체(호스트 결정부터 `continue`까지)가 정확히 한 번 있을 때만 패치한다.
    두 번 이상이면 오류로 멈추고, 이미 패치된 번들에는 다시 적용하지 않는다.
- 이 패치는 같은 청크에 같은 빌드의 수정 96 보호가 있을 때만 적용한다. 분류 함수의 worktree 검사
  이름이 같아야 한다. 보호 없이 모든 SSH 대화를 조회하면, 심볼릭 링크로 등록한 worktree 프로젝트의
  대화가 열지 않아도 모두 상위 저장소 프로젝트로 옮겨지기 때문이다.
- 관리용 데스크톱 복사본과 원본 동기화 복사본 모두 적용한다.
- 조회가 늘어난다. 비용과 그 사이의 표시는 아래 "조회 비용과 잠깐 사라지는 구간"에 정리했다.

### 사이드바 순서와 관계없는 배치 (수정 119 후속)

등록하지 않은 worktree 폴더의 대화는 같은 common dir을 쓰는 등록 프로젝트로 간다. 그런 프로젝트가
둘 이상이면(예: 상위 저장소와 등록된 worktree 프로젝트) 앱의 재배치 함수(`xIn`, 3930 `PIn`,
26.917 `vXr`)는 같은 저장소 상대 경로, 같은 루트 폴더 이름, 대화의 작업공간 힌트로 정하지 못할 때
**그 프로필의 사이드바 순서에서 첫 프로젝트**를 고른다. 실제 경로로 등록했으면 폴더 이름이 맞지 않을 때,
심볼릭 링크로 등록했으면 보통 상대 경로부터 맞지 않아서 이 선택이 결과를 정했다. 사이드바 순서는 프로필마다
따로 저장되므로 결과도 프로필마다 달랐다.

- `renderer_remote_order_patches()`를 추가했다. 이름 표 `_REMOTE_ORDER_VARIANTS`는
  `_remote_root_section` 옆에 있다. SSH 대화(`p`가 참)일 때만 재배치에 넘기는 프로젝트 목록을
  먼저 안정 정렬한다.
  1. 대화의 호스트에 등록된 원격 프로젝트 중 git 루트가 cwd의 git 루트와 같은 프로젝트.
     cwd가 들어 있는 등록 worktree다(예: 그 worktree의 하위 폴더).
  2. git 정보가 있고 자신은 linked worktree가 아닌 프로젝트. 저장소 프로젝트다.
  3. 나머지. 같은 순위 안에서는 사이드바 순서를 유지한다.
- 앱의 원래 규칙은 정렬된 목록에서 그대로 실행된다. 바뀌는 것은 사이드바 순서로 고르던 선택뿐이다.
  재배치는 프로젝트 경로만 돌려주므로 표시 순서는 바뀌지 않는다.
- 결과:
  - 등록하지 않은 worktree 폴더(와 그 하위 폴더)의 대화는 사이드바 순서와 관계없이 저장소 프로젝트로 간다.
  - 등록된 worktree 루트의 대화는 수정 96 보호가 그 프로젝트에 둔다. 정규 경로 표가 아직 없어
    보호가 판단하지 못할 때도 1순위로 그 프로젝트에 남는다.
  - 등록된 worktree의 하위 폴더 대화는 그 worktree 프로젝트로 간다. 전에는 심볼릭 링크 등록에서
    사이드바 순서를 따랐다.
  - 원격 Codex worktree(`~/.codex/worktrees/...`) 대화도 이름으로 프로젝트를 찾지 못하면 저장소 프로젝트로 간다.
  - 로컬 대화는 원래 목록을 그대로 쓴다.
- 이름: 26.917 `vXr`/`_Xr`/`qF`/`Ar`, 3930 `PIn`/`NIn`/`gj`/`Kf`, 4958 `xIn`/`bIn`/`lFn`/`yh`
  (재배치, linked worktree 검사, 폴더로 git 정보 찾기, 그 비교에 쓰는 경로 키). 분류 함수 안에서
  `t`는 사이드바 순서의 프로젝트 목록, `c`는 대화의 호스트, `d`는 cwd, `_`는 그 호스트의 git 정보다.
  실제 4958 렌더러와 관리용 3930 복사본에서 확인했다.
- 같은 청크에 같은 빌드의 분류 구간(보호 전 또는 후)이 정확히 한 번 있고 이름 표가 있을 때만,
  그 구간 안의 재배치 호출 한 곳을 바꾼다. 호출이 두 번 이상이면 오류로 멈춘다. 이미 정렬된
  번들에는 다시 적용하지 않는다. 두 복사본 모두 보호를 먼저 넣고, 그다음 순서, 요약 항목 조회를 넣는다.

### 26.930.3930 지원

- 3930의 분류 함수(`UIn`)와 폴더 선택 함수(`kIn`)는 4958과 이름만 다르다(관리용 3930 복사본에서 확인).
- `_SUMMARY_DIR_VARIANTS`에 3930(`Pc`, `Ch`)을 추가했다. 3930은 이제 거부되지 않고 세 패치가 모두 들어간다.
  수정 96 보호만 들어간 이전 3930 복사본에도 나머지 두 패치가 한 번씩 들어간다.
  3930의 `package.json` 버전은 `26.930.31730`이다.

### 호스트 보관 필터 (4958)

### 26.930은 조용히 빠지지 않는다

  이름 표에는 3930과 4958이 있다. 새 26.930 빌드에서는 세 이름 표(`_REMOTE_ROOT_VARIANTS`,
  `_REMOTE_ORDER_VARIANTS`, `_SUMMARY_DIR_VARIANTS`)를 함께 갱신해야 한다.

  같은 규칙을 따른다. 변형이 없으면 원래 동작으로 실행한다. 26.917에도 세 패치가 들어간다.
  핵심 연결 지점(프로필 통신, 알림, 대화 동기화)처럼 모든 버전에서 필수로 만들면 확인하지 않은
  버전이 모두 멈추기 때문이다.

### 조회 비용과 잠깐 사라지는 구간

- 사이드바는 호스트마다 대화 폴더 목록 전체를 한 번의 `git-origins` 요청으로 조회한다. 프로젝트
  루트는 따로 조회한다. 요약 항목 조회 패치 뒤에는 그 호스트의 SSH 대화 폴더(중복 제거)가 모두
  이 목록에 들어간다. 원격 호스트는 폴더마다 git 정보를 읽는다. 앱은 이 조회를 다시 실행한다
  (5초 뒤 오래된 결과로 보고, 조건에 따라 10초마다 다시 조회한다). 폴더가 많은 호스트에서는
  매번의 조회와 첫 사이드바 계산이 조금 길어진다.
- 폴더 목록이 바뀌면 조회도 새로 시작한다. 앱은 이전 결과의 폴더 목록이 새 목록을 모두 포함할
  때만 그 결과를 임시로 쓴다. 그래서 새 폴더가 생기면(처음 보는 폴더의 새 대화, 다른 창이나
  다른 프로필에서 만든 대화 등) 새 조회가 끝날 때까지 그 호스트의 대화 폴더 git 정보가 비어 있다.
- 이 사이에는 git 정보로만 배치되는 대화가 사이드바에서 잠깐 사라졌다가 조회가 끝나면 다시
  나타난다. 등록하지 않은 worktree 폴더와 그 하위 폴더, 등록된 worktree의 하위 폴더, 정규 경로 표가
  없을 때의 worktree 루트 대화가 해당한다. 정확한 경로나 정규 경로 표로 배치되는 등록 프로젝트
  루트의 대화는 영향이 없다. 폴더가 줄어들 때는 이전 결과를 쓰므로 사라지지 않는다.
- 원래 앱에서도 새 폴더의 대화를 열 때 같은 일이 생긴다. 패치 뒤에는 열지 않은 대화의 새 폴더도
  조회하므로 더 자주 생길 수 있다. 대신 이미 조회한 폴더의 대화를 열 때는 폴더 목록이 바뀌지 않는다.

### 남은 제한

- 순서 정렬은 사이드바 순서로 고르던 선택만 바꾼다. 앱의 루트 폴더 이름 규칙은 그대로 남는다.
  등록하지 않은 worktree 폴더의 이름이 등록된 worktree 프로젝트의 루트 폴더 이름과 같으면
  (예: 다른 위치의 `.../studio`) 이 규칙이 먼저 적용되어 그 프로젝트로 갈 수 있다. 실제 경로로
  등록한 경우가 해당한다. 이 결과도 사이드바 순서와는 관계없다.
- 위 "조회 비용과 잠깐 사라지는 구간".

## 우회 방법 (패치가 없는 버전)

패치가 들어간 복사본에서는 우회가 필요 없다. 보호와 순서 정렬이 사이드바 순서와 관계없이
등록된 worktree 루트의 대화는 그 프로젝트에, 등록하지 않은 worktree의 대화는 저장소 프로젝트에 둔다.

패치가 없는 버전에서는 수정 96 증상(등록된 worktree 프로젝트의 대화가 상위 저장소로 옮겨짐)을
**worktree 프로젝트를 상위 저장소 프로젝트보다 위로 끌어 올려** 피할 수 있다. 사이드바 순서는
프로필마다 저장되므로 증상이 있는 프로필마다 한 번씩 하면 된다. 이미 옮겨진 표시는 앱을 다시
시작하면 원래대로 돌아온다. 다만 이 순서에서는 등록하지 않은 worktree 폴더의 대화가 worktree
프로젝트로 간다. 반대 순서는 반대로 수정 96 증상을 낸다. 두 경우를 모두 맞추는 사이드바 순서는 없어서
순서 정렬 패치를 넣었다.

## 선택: 경로 등록 정리

SSH 프로젝트를 심볼릭 링크 경로 대신 대화가 기록하는 실제 경로(`/srv/...`)로
등록하는 것을 권장한다. 그러면 호스트 연결 상태와 `pwd -P` 정규 경로 표에 의존하지 않는다.
이 문제도 패치 없이 생기지 않는다.

이렇게 하면 따로 있는 작은 문제도 줄어든다. 프로젝트 화면은 등록 경로 그대로 대화 목록을
조회한다. 그래서 심볼릭 링크로 등록한 프로젝트는 실제 경로로 기록된 오래된 대화를
찾지 못하는 경우가 있다. 이 대화는 호스트 최근 목록에 들어 있을 때만 보인다.
