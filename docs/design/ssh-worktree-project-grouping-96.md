# 수정 96 — SSH worktree 프로젝트의 대화가 상위 저장소 프로젝트로 옮겨지는 문제

## 증상

SSH 호스트(`<ssh-host>`)에 git worktree 프로젝트와 그 상위 저장소 프로젝트를 함께 등록한 경우다.
일부 프로필에서 worktree 프로젝트의 대화를 하나 선택하면, 그 프로젝트의 대화가 모두
상위 저장소 프로젝트 아래로 옮겨졌다. worktree 프로젝트에는 `채팅 없음`이 표시됐다.

- 앱을 다시 시작하면 원래대로 돌아온다.
- 같은 대화라도 어떤 프로필에서는 증상이 나타나고 어떤 프로필에서는 나타나지 않았다.
- 제공자(DeepSeek, ChatGPT), 로그인, 관리자 동기화와는 관계없다.
- 대화 기록과 카탈로그 DB는 바뀌지 않는다. 사이드바 표시에만 생기는 문제다.

## 원인

Codex 26.917 렌더러의 사이드바 분류 코드(번들의 `DXr`)에서 생긴다.

1. 두 프로젝트는 심볼릭 링크 경로(`/home/<user>/projects/...`)로 등록되어 있다.
   대화의 작업 폴더(cwd)는 실제 경로(`/srv/...`)로 기록된다.
   worktree 폴더는 상위 저장소와 같은 git common dir을 쓰는 linked worktree다.
2. 앱을 시작하면 대화는 올바른 곳에 들어간다. 정확한 경로 비교와 호스트의 `pwd -P`
   정규 경로 표로 대화의 cwd를 worktree 프로젝트에 맞추기 때문이다.
3. 대화를 선택하면 그 대화는 요약이 없는 실행 중 항목이 된다. 앱은 이런 항목의 cwd로
   git 정보를 조회한다. 결과는 폴더 단위로 저장되므로 그 폴더의 대화 전체에 적용된다.
4. 조회 결과 cwd가 linked worktree로 확인되면 앱은 대화를 "같은 저장소의 프로젝트"로
   다시 배치한다(`vXr`). 이때 등록 경로(심볼릭 링크)와 git이 알려 준 실제 경로를 비교하므로
   정확히 맞는 프로젝트를 찾지 못한다.
5. 그러면 같은 common dir을 쓰는 프로젝트 중 **그 프로필의 사이드바 순서에서 첫 번째**
   프로젝트를 고른다. 상위 저장소 프로젝트가 위에 있는 프로필에서만 대화가 옮겨졌다.
   사이드바 순서는 프로필마다 따로 저장된다. 그래서 프로필마다 결과가 달랐다.

로컬 프로젝트에는 "cwd가 등록된 프로젝트 루트면 다시 배치하지 않는다"는 보호(`uXr`)가
원래 있다. SSH 프로젝트에는 같은 보호가 없었다.

## 수정

`scripts/manager_core/original_sync_bundle.py`에 `renderer_remote_root_patches()`를 추가했다.
관리용 데스크톱 복사본(`desktop_bundle.py`)과 원본 동기화 복사본 모두 렌더러를 만들 때
이 패치를 적용한다.

- SSH 대화의 cwd가 그 호스트에 등록된 프로젝트 루트와 같으면 다시 배치를 건너뛴다.
  경로가 정확히 같거나, 호스트의 정규 경로 표에서 같은 경로일 때가 해당한다.
  그 프로젝트가 대화를 그대로 가진다.
- 비교는 대화가 속한 호스트의 프로젝트끼리만 한다. 다른 호스트에 같은 경로가 등록되어
  있어도 영향을 받지 않는다.
- 로컬 대화는 바뀌지 않는다.
- 등록된 루트가 아닌 SSH cwd도 원래 동작 그대로다. `~/.codex/worktrees/...`, 하위 폴더,
  정규 경로 표가 아직 없는 경우(호스트 연결 전)가 여기에 속한다.
- 그래서 정규 경로 표가 없는 동안에는 패치가 아무것도 하지 않는다. 이때 cwd 조회가 먼저
  끝나면 증상이 잠깐 나타날 수 있다. 표가 채워진 뒤 사이드바가 다시 계산되면 worktree
  프로젝트로 돌아간다. cwd 조회와 정규 경로 조회는 둘 다 연결된 호스트에만 하므로 이 구간은 짧다.
- 26.917 렌더러에서 확인한 함수 전체가 정확히 한 번 있을 때만 패치한다.
  - 없으면 패치하지 않는다. 앱은 원래 동작으로 실행된다.
  - 두 번 이상 있으면 오류로 멈춘다.
  - 이미 패치된 번들에는 다시 적용하지 않는다.
- 26.915에도 같은 동작이 있지만 코드 모양이 달라 이번 패치 대상이 아니다.
  관리자가 26.915 복사본으로 실행하면 증상은 그대로 남는다.
- Codex가 새 버전으로 바뀌어 함수 모양이 달라지면 패치는 조용히 빠진다(원래 동작).
  번들 확인 검사는 26.917 복사본만 본다. 새 버전에서는 이름을 확인해
  `_REMOTE_ROOT_VARIANTS`에 변형을 추가해야 한다.
  26.930.4958에서 실제로 이렇게 빠졌다. 26.930은 이제 조용히 빠지지 않는다(아래 26.930.4958 절).

패치 파일이 바뀌면 관리용 데스크톱 복사본의 키도 바뀐다. 관리자를 다시 빌드한 뒤
프로필을 새로 실행하면 새 복사본이 만들어지면서 적용된다. 이미 실행 중인 프로필 창은
다시 시작해야 반영된다.

## 검사

`tests/test_desktop_remote_project_grouping.py`에서 다음을 확인한다.

- 패치 선택: 함수가 한 번 있으면 패치 하나를 만든다. 없거나 모양이 바뀌면 패치하지 않는다.
  두 번 있으면 거부한다. 이미 패치된 번들에는 다시 적용하지 않는다.

  - 패치 전: 상위 저장소가 위에 있고 cwd 조회가 끝나면 대화가 옮겨진다(증상 재현).
    순서가 반대면 옮겨지지 않는다.
  - 패치 후: 순서와 조회 여부에 관계없이 worktree 프로젝트에 남는다.
  - 원래와 같아야 하는 경우는 패치 전후 결과가 같다. 원격 Codex worktree, 원격 하위 폴더,
    정규 경로 표 없음, 실제 경로로 등록한 프로젝트, 로컬 루트, 로컬 worktree, 로컬 하위 폴더가 해당한다.
    다른 호스트의 대화도 포함한다. 그 cwd가 첫 호스트에 등록된 프로젝트의 정규 경로와 같아도
    원래대로 배치된다.
- 번들 확인: 이 컴퓨터에 관리용 26.917 복사본이 있으면 대상 함수와 보조 함수가 번들과
  정확히 같은지 확인한다.

## 26.930.4958 — 열지 않은 worktree 대화가 보이지 않는 문제 (수정 119)

### 증상

SSH 호스트에 저장소 프로젝트를 등록하고, 같은 git common dir을 쓰는 linked worktree 폴더는
프로젝트로 등록하지 않은 경우다. 그 worktree 폴더의 대화가 사이드바에 보이지 않았다.
그 창에서 대화를 하나 열면 그 폴더의 대화가 저장소 프로젝트 아래에 나타났다.
창마다 연 대화가 달라서 프로필마다 보이는 대화가 달랐다.

### 원인

1. 사이드바는 대화 폴더(cwd)의 git 정보를 조회한다. 조회할 폴더를 고르는 함수(번들의 `gIn`,
   26.917의 `pXr`)는 요약이 있는 항목, 즉 창에 로드되지 않은 대화를 건너뛴다.
   Codex worktree(`~/.codex/worktrees/...`) 안의 대화만 예외다.
2. 분류 함수(`AIn`)는 SSH 대화의 cwd가 등록된 프로젝트 루트가 아니면 git 정보로만
   저장소 프로젝트를 찾는다(같은 common dir 재배치). git 정보가 없으면 그 대화를 버린다(`if(p)return`).
3. 그래서 로드된 대화가 있는 폴더만 조회됐고, 나머지 worktree 대화는 표시되지 않았다.
4. 4958에서 분류 함수의 이름이 바뀌어 `_REMOTE_ROOT_VARIANTS`에 맞는 변형이 없었다.
   수정 96 보호가 조용히 빠져 있었고, 등록된 worktree 프로젝트의 대화를 열면 수정 96 증상도
   다시 생길 수 있었다.

### 수정

- `_REMOTE_ROOT_VARIANTS`에 4958 이름(`yFn`, `yIn`, `DIn`, `vIn`, `Yu`, `bIn`, `xIn`, `_Fn`, `mIn`)을
  추가했다. 실제 4958 렌더러(app-initial)에서 `_remote_root_section`이 한 번만 맞는 것을 확인했다.
- `renderer_summary_dir_patches()`를 추가했다. 폴더 선택 함수에서 요약 항목을 건너뛰는 조건을
  로컬 대화에만 적용한다(`n.summary!=null&&e===t&&!Yu(...)`; `e`는 대화의 호스트, `t`는 로컬 호스트).
  SSH 대화는 요약만 있어도 cwd를 조회한다.
  - 로컬 대화는 그대로다.
  - 프로젝트에 직접 지정된 대화, 프로젝트 없음으로 고정된 대화, `projectless` 대화, `~` 폴더 대화,
    연결된 원격 프로젝트가 없는 호스트의 대화는 기존 조건대로 조회하지 않는다.
  - 이름 표 `_SUMMARY_DIR_VARIANTS`에는 4958(`Fi`, `Yu`)과 26.917(`zs`, `R`)이 있다.
    대화 한 줄 처리 전체(호스트 결정부터 `continue`까지)가 정확히 한 번 있을 때만 패치한다.
    두 번 이상이면 오류로 멈추고, 이미 패치된 번들에는 다시 적용하지 않는다.
- 이 패치는 같은 청크에 같은 빌드의 수정 96 보호가 있을 때만 적용한다. 분류 함수의 worktree 검사
  이름이 같아야 한다. 보호 없이 모든 SSH 대화를 조회하면, 심볼릭 링크로 등록한 worktree 프로젝트의
  대화가 열지 않아도 모두 상위 저장소 프로젝트로 옮겨지기 때문이다.
- 관리용 데스크톱 복사본과 원본 동기화 복사본 모두 적용한다.
- 조회가 늘어난다. 연결된 SSH 호스트마다 대화 폴더(중복 제거)를 한 요청으로 묶어 조회한다.
  대화 폴더가 많은 호스트에서는 첫 사이드바 계산이 조금 늦어질 수 있다.

### 26.930은 조용히 빠지지 않는다

- 아카이브의 `package.json` 버전이 `26.930.`으로 시작하면, 렌더러(app-initial/app-shared) 중
  정확히 한 청크에 두 패치(수정 96 보호와 요약 항목 조회)가 모두 들어가야 한다.
  아니면 `patch_archive`가 `이 Codex 버전(...)의 SSH worktree 프로젝트 분류 위치를 확인하지 못했습니다.`
  오류를 낸다. 4958의 `package.json` 버전은 `26.930.41038`이다.
- 같은 관리 코드로 만든 이전 복사본이 없으면 관리용 앱을 만들지 않고 이 오류를 보여 준다.
  이름 표가 4958만 담고 있으므로 26.930.3930 같은 이전 26.930 빌드도 이 오류로 멈춘다.
  새 26.930 빌드에서는 두 이름 표를 함께 갱신해야 한다.
- 다른 버전(26.917, 26.915, 이후 새 버전)은 다른 선택 패치(호스트 보관 필터, 플러그인 갱신,
  수정 96 보호)와 같은 규칙을 따른다. 변형이 없으면 원래 동작으로 실행한다.
  핵심 연결 지점(프로필 통신, 알림, 대화 동기화)처럼 모든 버전에서 필수로 만들면 확인하지 않은
  버전이 모두 멈추기 때문이다.

### 남은 제한

- 등록하지 않은 worktree 폴더의 대화는 같은 common dir을 쓰는 등록 프로젝트로 간다.
  그런 프로젝트가 둘 이상이면(예: 상위 저장소와 등록된 worktree 프로젝트) 앱의 원래 규칙이
  사이드바 순서에서 앞선 프로젝트를 고를 수 있다. 이때는 프로필마다 결과가 다를 수 있다.
  저장소 프로젝트를 그런 프로젝트들보다 위에 두면 모든 프로필에서 저장소 프로젝트로 모인다.

  두 번 있으면 거부한다. 보호가 없거나 다른 빌드의 보호면 패치하지 않는다.

  청크를 지정하면, 위 함수들이 번들과 정확히 같은지와 두 패치가 각각 한 번 적용되는지 확인한다.
- 실제 4958 아카이브에 두 복사본 패치를 적용하면 app-initial에 두 패치가 들어가고,
  바뀐 청크가 `node --check`를 통과한다.

## 우회 방법 (패치 적용 전)

증상이 있는 프로필의 사이드바에서 **worktree 프로젝트를 상위 저장소 프로젝트보다 위로
끌어 올린다.** 사이드바 순서는 프로필마다 저장되므로 증상이 있는 프로필마다 한 번씩 하면 된다.
이미 옮겨진 표시는 앱을 다시 시작하면 원래대로 돌아온다.

## 선택: 경로 등록 정리

SSH 프로젝트를 심볼릭 링크 경로 대신 대화가 기록하는 실제 경로(`/srv/...`)로
등록하는 것을 권장한다. 그러면 호스트 연결 상태와 `pwd -P` 정규 경로 표에 의존하지 않는다.
이 문제도 패치 없이 생기지 않는다.

이렇게 하면 따로 있는 작은 문제도 줄어든다. 프로젝트 화면은 등록 경로 그대로 대화 목록을
조회한다. 그래서 심볼릭 링크로 등록한 프로젝트는 실제 경로로 기록된 오래된 대화를
찾지 못하는 경우가 있다. 이 대화는 호스트 최근 목록에 들어 있을 때만 보인다.
