# 수정 120 — 런타임 시작 실패 재시도, 시작 실패 뒤 오류창 정리

## 1. 사용자가 만난 증상

- 관리창을 연 직후 한 프로필이 "ChatGPT failed to start. (code=3221225477) … finalizing (tstate=…) <no Python frame>" 창을 띄우고 열리지 않았다.
- 기록(`runtime-state.json`의 `last_exit`, 수정 119):
  - 관리 런타임은 시작 1.2초 만에 `0xC0000142`(STATUS_DLL_INIT_FAILED)로 끝났다.
  - 그 결과를 앱에 넘기던 런타임 프록시(Python)가 인터프리터 종료 중에 `Fatal Python error: _enter_buffered_busy`로 죽었다.
  - 앱은 런타임의 코드 대신 프록시의 `0xC0000005`(3221225477)를 받았다.
- 같은 시각 Windows에 "가상 메모리 부족" 경고가 있었고, 다른 프로필의 런타임도 `0xC0000409`로 끝났다.
  - 커밋 메모리가 한도에 가까운 상태(약 78 / 100 GB)에서 프로필 11개가 한꺼번에 시작했다.
  - 이때 새 프로세스의 DLL 초기화(콘솔 호스트·힙 할당)가 실패했다.

## 2. 원인

1. **DLL 초기화 실패(`0xC0000142`).** 런타임 코드가 실행되기 전 Windows 로더 단계의 실패다. 같은 실행 파일을 잠시 뒤 다시 시작하면 대개 성공한다. 이전에는 재시도가 없어서 프로필이 그대로 실패했다.
2. **프록시 종료 중 강제 중단.**
   - 앱 입력을 읽는 데몬 스레드가 `sys.stdin`의 `BufferedReader.read1` 안에서 잠금을 쥔 채 막혀 있었다.
   - 런타임이 먼저 끝나면 인터프리터 종료가 그 `sys.stdin`을 닫으려다 잠금을 얻지 못해 중단됐다.
   - 그 결과 원래 종료 코드가 사라졌다.
3. **런타임마다 콘솔 호스트 하나 더.** 프록시가 런타임을 `CREATE_NO_WINDOW`로 시작해, 런타임마다 별도 콘솔 호스트(conhost)가 생겼다. 프로필이 많을 때 시작 순간의 프로세스·메모리 부담을 더한다.

## 3. 변경(`scripts/manager_core/runtime_proxy.py`)

- **입력 읽기:** 앱 입력은 `os.read`로 직접 읽는다(`RawInput`). 잠금이 없으므로 종료가 막히지 않는다.
- **종료:** `__main__`은 항상 `os._exit(런타임 종료 코드)`로 끝난다.
  - NTSTATUS 코드는 같은 32비트로 넘긴다(`exit_status`).
  - 예상하지 못한 예외는 고정 문구 한 줄과 코드 70으로 끝낸다. 예외 문장에 경로·프로토콜 값이 담길 수 있어 보여 주지 않는다.
- **시작 실패 재시도:** `0xC0000142`만 다시 시작한다.
  - 0.5초, 2초에 각각 0~50% 지연을 더해 최대 2회 재시도한다.
  - 다음 조건을 모두 만족할 때만 재시도한다:
    - 런타임이 아무것도 출력하지 않았다.
    - initialize가 끝나지 않았다.
    - 시작 후 10초가 지나지 않았다.
    - 관리 쓰기가 아직 없었다.
    - 보관한 입력이 4 MiB 이하다.
  - 접근 위반(`0xC0000005`)은 런타임 코드가 실제로 죽은 것이므로 재시도하지 않는다.
- **입력 보관(`RuntimeInput`):**
  - 재시도가 가능한 동안 앱이 보낸 프레임을 인증·권한·관찰 처리를 거친 그대로 보관한다.
  - 새 런타임에는 같은 바이트를 먼저 넘긴다. 앞쪽 처리는 다시 실행하지 않는다.
  - 재시도가 불가능해지면 보관을 끝낸다(봉인). 봉인 전에 끝난 런타임에 쓰다 실패한 기록은 대체가 없을 때에만 프로토콜 누락으로 알린다.
- **관리 연결:**
  - 새 런타임이 시작되면 관리 연결(`AdminServer.rebind_runtime`)이 새 프로세스 ID를 가리킨다.
  - 새 런타임의 출력 읽기나 관리 연결 준비가 실패하면 새 런타임을 끝내고, 원래 시작 실패 코드를 앱에 넘긴다.
- **콘솔 공유:**
  - 프록시에 콘솔이 있으면 런타임이 그 콘솔을 같이 쓴다. 콘솔이 없을 때만 `CREATE_NO_WINDOW`를 쓴다.
  - 같은 콘솔의 Ctrl+Break가 프록시를 끝내지 않도록 SIGBREAK를 무시한다.
- **상태 기록:**
  - `runtime-state.json`에 `start_retries`(재시도된 시작 실패의 코드·시작 후 시간·시각)를 남긴다.
  - `last_exit.retries`에는 재시도 횟수를 남긴다.
- **`runtime_admin.AdminServer.start`:** 수락 스레드를 시작하지 못하면 게시한 연결 정보를 거둔다.

## 4. 상태 보고(`scripts/health_report.py`)

- `runtime_start_retries` 항목과 한국어 요약 줄을 추가했다. 예: "시작 재시도 후 복구된 런타임: N개 프로필 (… 시작 재시도 1회 · 실패 종료 코드 3221225794)".
- 마지막 시작까지 실패한 런타임은 기존 "빠른 종료" 줄에 재시도 횟수와 함께 나온다.

## 5. 검증

- 단위 테스트(`test_manager_runtime_proxy`, `test_manager_runtime_admin`, `test_manager_health_report`, `test_manager_pipe_writer`, `test_manager_ssh_shim`) 99개 통과.
- 새 테스트 10개는 수정 전 코드에서 모두 실패했다. 다룬 경우:
  - 실제 진입점의 예외 처리
  - 봉인 쓰기 실패 시 누락 보고
  - 느린 프로세스 생성의 시작 시간 계산
  - 출력 읽기 실패 시 새 런타임 정리
  - 빠른 접근 위반을 재시도하지 않음
  - 관리 연결 재바인딩 실패
  - 수락 스레드 실패 시 연결 정보 정리
- 전체 Python 테스트(`test_launchers` 제외): 2,285개 실행, 실패 0, 건너뜀 71.
  - 워크트리 환경 오류가 2건 있었다: 외부 `llm_usage` 경로와 SshProxy Release 빌드 없음.
  - `test_manager_remote_accounts`는 main에서 통과했다.

## 6. 적용과 남은 과제

- 프록시는 관리자 릴리스 폴더에서 실행되므로, 관리자 빌드(수정 120)와 완전 종료 뒤 다시 열어야 적용된다.
- 근본 원인은 시스템 커밋 한도다. 페이지 파일 크기와 동시에 켜 둘 프로필 수는 사용자가 정한다.

  - 런타임·관리자 릴리스 변경 시 단계적 재시작
