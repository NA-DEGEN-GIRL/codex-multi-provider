# 수정 94: 공급자를 바꿔도 이어지는 대화 문맥

## 문제

프로필끼리 같은 작업을 공유하므로 한 작업을 GPT로 하다가 다음 턴을 외부 API(DeepSeek 등)로
이어 갈 수 있다. 이전 런타임에서는 다음 두 경우에 문맥이 끊겼다.

- GPT가 자동 압축을 하면 그 이전 대화는 OpenAI만 읽을 수 있는 암호화 상태 하나로 바뀐다. 다른
  공급자는 이것을 읽지 못해 요청이 실패하거나 압축 이전 대화를 조용히 잃었다.
- GPT의 암호화된 추론·에이전트 간 메시지·도구 출력이 다른 공급자로 그대로 가면 같은 문제가
  생긴다. 반대 방향(외부 공급자의 상태를 GPT로)도 마찬가지다.

## 방식

공급자를 **family**로 묶는다. OpenAI·Azure Responses는 OpenAI family이고, 나머지 공급자는 각자
설정 id가 family다. family 안에서는 서로의 암호화 상태를 읽을 수 있다고 본다.

### 압축할 때 평문 요약도 남김

- 압축 기록(`CompactedItem`)에 만든 family(`origin`), 평문 요약(`portable`: 요약·상태·덮는 범위),
  종류(`kind`)를 더한다. 이 필드가 없는 이전 기록도 그대로 읽는다.
- 평문 요약은 압축과 함께 요청한다. 압축이 끝난 뒤 30 s까지 기다리고, 늦거나 실패하면 실패로
  기록하고 작업을 계속한다(경고 표시).
- 수정 95: 요약 요청은 압축 요청을 그대로 복사하고 마지막 압축 지시만 요약 지시로 바꾼다. 도구·
  기본 지시문·effort·서비스 등급이 같아 앞부분이 캐시에 맞는다. 수정 94는 도구를 비우고 low
  effort로 보내 매 압축마다 전체 문맥(중앙값 약 22.7만 token)을 캐시 없이 읽었다. 요약 답에 도구
  호출이 있으면 실행하지 않고 실패로 기록한다(서버 쪽 도구는 이미 실행됐을 수 있다). 체크포인트에
  요약 요청의 사용량(`usage`)과 걸린 시간(`elapsed_ms`)을 남긴다. 실측(06, `gpt-6-astra`):
  입력 9,114 중 8,832 token이 캐시(97%), 5.9 s.
- 비용은 다른 family가 이어 받을 수 있을 때만 쓴다. 기록에 이미 다른 family가 있거나, 관리
  앱의 공유 실행이고 이 프로필에 다른 family의 공급자가 설정된 경우다. 하위 에이전트는 자기
  기록에 다른 family가 보일 때만 요약한다.

### 이어 받을 때의 우선순위 (`build_context`)

작업이 다른 family로 넘어가거나, 그대로 보내면 다른 family의 암호화 상태가 섞일 때만 문맥을
새로 만든다. 수정 96부터는 받는 family가 전에 이 작업을 떠날 때 남긴 복귀 기준점이 있으면 먼저
자기 이전 문맥을 이어 붙인다(아래 "수정 96: 돌아온 family의 이어 붙이기"). 기준점이 없거나 확인에
실패하거나 크기 한도를 넘을 때만 다음 순서로 새로 만든다.

1. 받는 family 자신의 최신 압축 + 그 뒤 기록.
2. 전체 대화가 받는 모델의 예산에 들어가면 전체 대화.
3. 최신 평문 요약 + 그 뒤 기록(그 앞의 사용자 메시지 포함).
4. 요약 + 빠진 턴의 사용자 메시지 + 무엇이 빠졌는지 알리는 메모 + 들어가는 최신 턴들.
   턴 하나도 다 들어가지 않으면 그 턴의 최신 항목만 넣는다(도구 호출과 출력은 함께).
5. 요약도 없으면 오래된 문맥이 없다는 메모와 최신 턴.

- 다른 family의 암호화 상태는 빼고, 추론은 평문 요약을 assistant 메시지로 옮긴다. 암호화된
  메시지·도구 출력은 설명 문구로 바꾸고 경고를 남긴다.
- 크기 추정은 런타임의 byte 기반 추정에 안전 계수를 둔다(한글 1음절 ≈ 1.5 token).
  남기는 사용자 메시지는 최신부터 20k token까지다.
- 새로 만든 문맥은 받는 family의 `rebuilt` 체크포인트로 기록한다. 같은 family로 다시 열 때는
  다시 만들지 않고, 지난 설정 묶음·모델 전환 메시지가 쌓이지 않는다. 이 체크포인트는 아무
  것도 요약하지 않으므로 다른 family는 그 앞 기록을 그대로 읽는다. 수정 96부터 이 체크포인트에
  떠나는 family의 복귀 기준점(`return_anchors`)도 적고, 설정 차이만 있는 턴에서도 기록한다.
- 수정 96: 모델 전환 메시지를 지우는 단계가 설정 묶음이 아닌 developer 메시지(예: 클라이언트가
  넣은 메시지)의 내용을 비워 `content: []`로 보내던 문제를 고쳤다.
- 부모 작업에서 이어 받은 첫 체크포인트(fork, 하위 에이전트)는 덮는 범위를 이 작업 기록과
  대조하지 않고 받아들인다. 작업 안에서 되돌린 체크포인트는 여전히 거절한다.

### 수정 96: 돌아온 family의 이어 붙이기

위 재구성은 돌아온 family의 이전 설정 묶음과 기록 앞부분을 다시 만들기 때문에 캐시가 도구·지시문
근처에서 끊겼다. 수정 96은 돌아온 family가 떠날 때 보던 문맥을 그대로 앞에 둔다.

- 떠날 때: 넘겨받는 family가 문맥을 새로 만들 때, 떠나는 family의 기준 체크포인트와 마지막 기록의
  위치, 그 구간 기록의 SHA-1 요약값, 마지막 턴 설정·world-state 스냅샷, 마지막 요청 머리말 해시를
  자기 `rebuilt` 체크포인트에 기준점으로 적는다. 그 구간을 떠나는 family의 규칙으로 다시 그린
  결과가 실제 재생과 같을 때만 적는다.
- 돌아올 때: 최근 체크포인트부터 자기 기준점을 찾는다. 요약값이 같고, 구간 안에 다른 체크포인트나
  새 문맥 창이 없고, 기준점 뒤에 자기 기록이 없고, 앞부분에 읽을 수 없는 다른 family 상태가 없어야
  한다. 그러면 자기 이전 문맥 + `<provider_handoff>` 메모 한 줄(약 30 token) + 다른 family의 턴(위의
  변환 규칙 적용, 설정 묶음·전환 메시지 제외)을 보낸다.
- 이전 턴 설정과 world-state 기준을 되살리므로 다음 턴에는 설정 차이만 붙고, 모델이 같으면
  `<model_switch>` 메시지가 붙지 않는다. 결과는 `spliced` 표시가 있는 `rebuilt` 체크포인트로
  기록되어 이후 일반 재개도 같은 문맥을 재생한다.
- 크기 한도: 기본값은 자동 압축 기준 아래(재구성과 같은 여유를 뺀 값)에 들어갈 때만 이어 붙인다.
  넘으면 위 순서로 재구성한다. 런타임 환경 변수 `CODEX_PORTABLE_SPLICE=compact`면 문맥 창까지
  이어 붙이고 자동 압축 기준을 넘으면 첫 요청 전에 압축하며, `off`면 이어 붙이기를 끈다.
- 확인에 실패하면 이유를 로그(`codex_core::portable_context::splice`)에 남기고 위 순서로 재구성한다.
- 알려진 한계: 넘겨받은 family가 첫 메시지 전에 압축하면 떠난 family의 기준점이 기록되지 않아
  다음 복귀는 재구성된다.
- 배경, 절약 추정, 적용 뒤 확인: [switch-cache-optimization-96](switch-cache-optimization-96.md).

## 호환

- 이전 런타임은 새 필드를 무시하고 최신 체크포인트부터 읽는다. 새 런타임과 이전 런타임이
  같은 기록을 번갈아 써도 기록을 읽을 수 있다.
- 공급자 전환이 없는 작업은 이전과 같은 요청을 보낸다(수정 96부터 원격 압축이 없는 공급자의
  압축 요청은 턴 요청과 같은 도구·설정을 보낸다). 기록에 추가되는 것은 압축 기록의 새
  필드와 사용량 기록의 `served_by`(수정 96)뿐이다. 수정 96의 기준점 필드(`return_anchors`, `spliced`)도 선택 필드라 이전 런타임은
  무시하고 최신 체크포인트부터 읽는다.
- 나중에 Claude 같은 공급자를 연결해도 별도 family가 되어 같은 규칙으로 이어 받는다.

- 런타임 crate 시험(history, rollout, state, app-server-protocol, thread-store) 통과.
  `portable_context` 통합 시험 27개 통과. app-server 전체 1,119개 통과, 기존 실패 21개(목록 동일).
- 여러 단계 탐침: GPT→DeepSeek→GPT(legacy·paginated), GPT↔xAI, 압축 중간 도구 출력, 한글 예산,
  이어 받은 체크포인트(E2·E2b), 재구성 체크포인트의 요약 전달(E3), 반복 전환 뒤 손자 작업(E4),

  않았고 요약은 한 번씩만 들어갔다.
- 각 수정을 되돌리면 해당 시험이 실패함을 확인했다.

  복원 트리 `9c13823a…`, 305개 파일. 수정 95의 `portable_context` 통합 시험 29개, app-server 전체
  1,121개 통과(기존 실패 21개 동일).
- 수정 96 패치 `64e93624…50d0`, 복원 트리 `c5ab141c…`, 316개 파일. `portable_context` 통합 시험
  35개(이어 붙이기 6개 추가), app-server 전체 1,123개 통과(기존 실패 21개 + 단독 실행 시 통과하는

## 실제 공급자 확인 (2026-09-26, `scripts/test_cross_provider_context_live.py`)

- 06(`gpt-6-astra`) → 압축 → DeepSeek API 프로필(`deepseek-flash`) → 06: 모두 정답. DeepSeek 요청에 암호화 항목 0개.
- 요약 경로: DeepSeek 문맥 한도를 32k로 줄여 원래 메시지 없이 평문 요약만 받게 했을 때도 정답.
- 계정 간: 06의 네이티브 압축을 01이 그대로 이어 받아 요청이 받아들여지고 답도 맞았다(압축이
  사용자 메시지를 원문으로 남기므로 해독까지 증명한 것은 아니다).
- 테스트는 임시 기록 저장소를 쓰고 06·01은 access token만 빌렸다. 비밀정보 검사 통과, 임시 폴더 삭제.

## 적용

- Windows 런타임 후보는 `artifacts/manager-runtime/releases/`에 스테이징하고 공유 실행·공통 저장소
  검증 보고서로 활성화한다. 새로 여는 프로필부터 적용되므로 완전 종료 후 모두 같은 런타임으로
  시작한다.
- SSH용 Linux 묶음은 같은 패치로 빌드한다(수정 95: `0.153.4-managed-d7ab12a792bcd355`). 원격 적용은 SSH
  업데이트 화면의 규칙을 따른다.

## 확인하지 못한 것

- 실제 공급자로의 전환(GPT↔DeepSeek, GPT 압축 → DeepSeek → GPT)은 적용 후 확인해야 한다.
- 수정 96의 이어 붙이기는 오프라인 시험(모의 서버)으로만 확인했다. 실제 공급자에서 캐시가 맞는지는
  적용 후 사용량 장부와 요청 앞부분 비교 로그로 확인한다.
- 서로 다른 ChatGPT 계정이 서로의 암호화 항목을 읽을 수 있다고 가정한다. 계정 사이에서 이것이
  거절되면 같은 OpenAI family 안에서도 재구성이 필요하다.
- 요약 품질은 모델 응답에 달려 있다. 요약이 실패한 압축은 4·5단계로 이어 받는다.
- 이름이 OpenAI인 중계 공급자도 OpenAI family로 본다.
