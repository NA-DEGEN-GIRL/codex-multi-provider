# 수정 106 — 작업 화면 이동 확인과 재시작 없는 복구

## 관찰한 문제

작업 바로가기를 누르면 `conversation.open`은 `request_sent`를 반환했지만 화면이
선택한 작업으로 바뀌지 않았다. 실행 프로세스와 창은 살아 있었으며 해당 계정의
원격 작업도 진행 중이었다. 렌더러 응답 측정에 오래된 대기 기록이 있었으나,
이것만으로 렌더러 충돌이나 모든 입력 지연의 원인을 확정하지 않는다.

실행 중인 창의 기존 navigation 파일 통로로 정확한 작업과 SSH host ID를 전달하자
acknowledgement와 `active-task.json`의 선택 기록이 일치했다. 앱 프로세스를
재시작하지 않았고 사용자가 정상 동작을 확인했다. 이 성공한 경로를 자동화한다.

## 동작

1. `MainWindow.OpenShortcutAsync`는 기존 열기 요청과 창 연결을 수행한 뒤 관리
   작업 잠금을 해제한다. `VerifyShortcutNavigationAsync`는 별도로 화면을 확인한다.
2. 서비스가 반환한 정확한 작업 URI를 검사한다. 편집 가능한 `request_sent`에만
   적용하며 읽기 전용 기록, 다른 작업·호스트, 중복 URI 인자는 거절한다.
3. 현재 선택, 프로필 실행 세대, PID와 창 핸들이 모두 같은지 확인한다. 일반 이동에
   2초를 주고, 아직 창이 연결되지 않았으면 최대 25초까지만 기다린다.
4. 선택 기록이 여전히 다르면 `NativeWindowLease.NavigateAsync`로 해당 창에
   직접 이동을 **한 번만** 전달한다. 전역 상태 조회, 로그인 또는 모델 실행을
   추가하지 않는다. 전달은 최대 8초, 이후 화면 선택은 최대 6초 더 확인한다.
5. acknowledgement만으로 성공으로 표시하지 않는다. 실제 선택된 작업·SSH 호스트를
   확인해야 성공이다. 사용자가 다른 프로필·작업으로 이동하면 요청을 취소한다.
6. 취소 시 아직 전달되지 않은 자기 요청 파일을 제거한다. 더 최신 요청은 보존한다.
   무한 재시도, Electron reload, 프로필 재시작, 실행 중 작업 중단은 하지 않는다.

진단 로그에는 복구 결과만 남긴다. navigation lease의 비밀값, 대화 본문, 계정 인증은
기록하지 않는다. 완전히 응답하지 않는 렌더러까지 복구한다고 보장하지 않으며,
이 경우 화면 이동 미확인을 표시하고 자동 시도를 끝낸다.

## 관련 코드

- `manager/Shell/MainWindow.ShortcutRecovery.cs`: 관리창의 선택·창 수명 확인과 결과 표시.
- `manager/Shell/ShortcutNavigationRecovery.cs`: URI 검사, 대기·한 번 전달·취소 정책.
- `manager/Shell/NativeWindowLease.cs`: 고유 임시 파일과 취소된 전달 파일 회수.
- `manager/Shell/ShortcutRecoverySelfTest.cs`: 복구 정책과 실제 파일 전달 검사.
- `manager/Shell/ShortcutNavigationSelfTest.cs`: 기존 전환 검사에 복구 검사를 연결.

기존 데스크톱의 `desktop_notification_activation.cjs` navigation hook을 그대로
사용한다. 이번 수정은 WPF 관리창에서 동작하며 새 네이티브 런타임이 필요하지 않다.

## 적용

게시한 관리창은 `artifacts/manager/releases/20261001-171017-309`이다. 217개 고정
파일 해시와 자체 시험 확인 후 관리 앱의 `current.json`만 이 빌드로 게시했다.
Windows 네이티브 실행기와 Linux 기본 배포 포인터는 변경하지 않는다.
이전 관리창 포인터는 `work/manager-current-before-106.json`에 보존했다.

현재 실행 중인 수정 99 관리창에는 이 코드가 들어 있지 않다. 관리창을 X로 닫고
다시 열면 수정 106이 기존 서비스와 프로필에 연결한다. `ManagerClient.ConnectAsync`는
기존 서비스에 실행 중 프로필이 있으면 서비스 교체를 보류한다. 이번 화면 복구를
적용하려고 완전 종료할 필요는 없다. 수정 102–105의 네이티브·SSH 기능 활성화는
각 문서의 별도 검증과 작업 종료 조건을 따른다.

## 후속 구조 검토

장기적으로 화면 하나와 계정별 실행 환경을 분리하는 방향이 타당하다. 계정별로
Electron 화면 전체를 유지하는 부담은 줄일 수 있지만, 작업의 계정·공급자·프리셋·
실행 호스트·워크트리 연결과 권한 요청은 독립적으로 유지해야 한다. 전역 로그인만
교체하면 동시에 실행 중인 작업과 브라우저·플러그인의 계정 경계가 깨질 수 있다.

[공식 App Server 문서](https://learn.chatgpt.com/docs/app-server)는 인증, 대화 이력,
승인 요청, 스트리밍 이벤트를 갖춘 별도 클라이언트 구현을 지원한다. 원본 데스크톱의
모든 기능을 그대로 재사용하거나 다중 계정 UI가 자동으로 지원된다는 보장은 아니다.
원본 화면을 유지하는 방식은 데스크톱 연결 계층을 수정하고 업데이트마다 브라우저,
플러그인, 승인, 알림을 검증해야 한다. 이 문서의 구조 제안은 설계 판단이며 아직
구현하지 않았다. 첫 실험 범위는 화면 하나에서 두 계정과 SSH 작업을 동시에 실행하고
각 계정의 승인·도구·알림이 정확한 작업에 전달되는지 확인하는 것이다.
