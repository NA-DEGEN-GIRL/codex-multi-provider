# 실행 중 서비스 기준 업데이트 안내 — 수정 78

관리창만 닫고 다시 열면 작업을 실행 중인 관리 서비스는 남아 있을 수 있습니다.
기존 안내는 새 관리창이 있고 IPC와 작업 유지 기능이 같으면 먼저 ‘작업 유지하며
업데이트 가능’을 반환했습니다. 서비스 변경 여부는 관리창이 이미 최신인 경우에만
확인해서, 서비스 적용이 대기 중인데 다음 빌드가 나오면 다시 초록색으로 바뀌었습니다.

수정 78은 실행 중인 서비스의 `supervisor.status.service_revision`을 선택된 배포의
`runtime-manifest.json.service_revision`과 **먼저 비교**합니다. 서비스 응답의 값은
실제 서비스 실행 파일 옆의 불변 배포 정보에서 시작 시 읽으며, 설치 포인터에서
추정하거나 현재 관리창의 버전으로 대체하지 않습니다.

| 상태 | 표시 |
| --- | --- |
| 새 관리창이 있고 실제 서비스와 배포의 서비스 해시가 일치 | 작업 유지하며 업데이트 가능 |
| 관리창이 최신이고 실제 서비스도 배포와 일치 | 관리창 최신 · 작업 유지 가능 |
| 실제 서비스 해시가 다름 | 작업 종료 후 적용 필요 |
| IPC가 다르거나 구버전 서비스가 작업 유지를 지원하지 않음 | 작업 종료 후 적용 필요 |
| 실행 서비스 또는 배포 정보 누락·잘못된 형식 | 업데이트 호환성 확인 불가 |

서비스 해시는 64자리 16진수인지 검증합니다. ‘작업 종료 후 적용 필요’ 상태는 관리창만
다시 열거나 다음 빌드가 등장해도 그대로 남습니다. 실제 서비스가 필요한 배포로
교체된 응답을 받아야 해제됩니다. 서비스 응답 조회와 배포 정보 읽기만 수행하며,
이 검사 자체는 작업·프로필·서비스를 중단하거나 교체하지 않습니다.

격리된 호환성 검사에서는 서비스 A가 남은 상태에서 관리창 B로 재실행하고 다시
배포 C가 등장하는 순서를 재현합니다. 관리창만 변경된 배포는 안전한 재실행으로
계속 판정하는지, 같은 관리창이라도 서비스가 오래되면 종료 안내를 유지하는지,
누락·손상된 정보가 안전한 업데이트로 표시되지 않는지도 확인합니다.

## 관리창 변경과 서비스 변경 구분

서비스 파일에는 코드가 같아도 Git 커밋 정보가 바뀌면 다시 생성되는 .NET 빌드
정보가 포함되어 있었습니다. 이 때문에 관리창만 바꾼 커밋에서도 서비스 해시가
달라질 수 있었습니다. RuntimeProxy·SSH 실행기·공통 라이브러리에서는 커밋별
InformationalVersion과 SourceLink 정보를 제외해 동일한 소스의 출력이 같게 합니다.
실행 파일·Python 코드의 실제 내용 해시는 계속 비교하므로 서비스 코드가 바뀐
경우를 호환된다고 숨기지 않습니다. 이 빌드 설정을 처음 적용할 때는 서비스 파일의
해시가 한 번 변경될 수 있습니다.

## 검증

- 호환성 상태와 파일 불변성 52개 검사를 포함한 전체 Windows 빌드 자체 검사를 통과했습니다.
- 배포 번들 검사 6개를 통과했습니다.
- 서로 다른 합성 Git 커밋 ID 두 개로 강제 재빌드한 결과, 위 세 프로젝트의 DLL·EXE·PDB
  출력 8개가 모두 바이트 단위로 같았습니다. 실제 실행 파일의 내용 해시 비교는 유지합니다.
- 실제 사용 중인 관리 서비스·프로필·SSH 작업은 종료하거나 업데이트하지 않았습니다.
