# SSH 강제 재부팅 후 작업 기록 복구

2026-09-25 구현·확인. 이 절차는 원격 관리 프로필의 **한 작업**에만 적용한다.
서버 재부팅 뒤의 브라우저 연결 실패와 작업 기록 손상은 별개로 진단한다.

## 먼저 증상을 구분한다

- 원격 웹 서버에서는 HTTP 응답이 오지만 Windows의 같은 `127.0.0.1` 주소는
  연결 거부: Windows → SSH 포트 전달이 없는지 확인한다. SSH 작업 연결과
  웹 포트 전달은 별개다. 앱 전체 재실행이 해결을 보장하지 않는다.
- `durable rollout shrank before projection`: 조회용 DB의 저장 위치가 실제
  JSONL 기록 파일 길이를 넘었다. 캐시 DB와 원본 파일을 각각 확인한다.
  재로그인·프로필 삭제·전체 DB 삭제로 해결하지 않는다.

포트 전달 예시(호스트·포트는 실제 프로젝트에서 확인):

```powershell
ssh -N -T -o ExitOnForwardFailure=yes -o ServerAliveInterval=15 -o ServerAliveCountMax=3 -L 127.0.0.1:3410:127.0.0.1:3410 <ssh-host>
```

이 명령은 자동 재연결 서비스가 아니다. 서버가 다시 내려가면 종료될 수 있다.
연결 후 **Windows에서** 해당 URL의 HTTP 응답과 실제 화면을 확인한다.

## 기록 복구 도구

[`scripts/remote_helpers/history_repair.py`](../../scripts/remote_helpers/history_repair.py)는
Linux 서버에서 실행하는 수동 유지보수 도구다. 기본 동작은 검사이며 자동 복구나
앱 시작 시 무조건 실행하는 기능이 아니다. 전체 앱·원격 서비스를 종료하지 않는다.

먼저 작업 ID를 `state_5.sqlite.threads`에서 찾아 **원본을 가진** 프로필의
`rollout_path`를 확인한다. 현재 열어 둔 Windows 프로필과 원본 프로필이 다를 수 있다.
일반적인 원본 HOME은 다음과 같다.

```text
/home/<ssh-user>/.local/share/codex-control-center/profiles/<source-profile-uuid>/codex
```

저장소의 도구를 해당 서버의 사용자 전용 임시 폴더에 복사하거나, 서버에 복원한
저장소에서 실행한다. 다음은 **서버의 셸**에서 실행하는 명령이다.

```bash
python3 scripts/remote_helpers/history_repair.py \
  --home /home/<ssh-user>/.local/share/codex-control-center/profiles/<source-profile-uuid>/codex \
  --thread <task-uuid>
```

검사 결과가 대상 작업과 일치하며 복구 대상 작업이 실행 중이 아닐 때 같은 명령에
`--apply`를 추가한다. 일반 SSH 사용자로 실행한다. 전체 명령을 `sudo`로 실행하여
기록·잠금 파일의 소유자를 root로 바꾸지 않는다.

보호된 같은 사용자 프로세스 때문에 `/proc` 확인을 할 수 없는 서버에서는,
읽기 전용 관리자 조회가 허용되어 있고 `sudo -n`이 구성된 경우에만
`--inspect-proc-with-sudo`를 추가할 수 있다. 이 옵션은 프로세스 파일 사용 여부만
관리자 권한으로 확인한다. 실패하면 기록 변경을 보류한다.

### 적용 조건과 보존 범위

- 선택한 관리 HOME·작업 ID·원본 파일 위치가 일치해야 한다. 심볼릭 링크와
  하드 링크를 통한 다른 저장소 수정은 거부한다.
- 원본은 0부터 연속된 ordinal을 가진 완전한 JSONL 접두부여야 한다.
  마지막 **불완전한** 한 줄만 분리할 수 있다. 완전한 줄의 손상, ordinal 누락,
  줄바꿈만 없는 유효 JSON은 자동으로 잘라내지 않는다.
- 적어도 한 조회 DB의 체크포인트가 실제 파일 길이를 초과해야 한다.
- 원본의 고정된 과거 구간을 참조하는 포크 등 안전하게 복구할 수 없는 계보는 거부한다.
- 원본의 프로필별 작성 잠금, 공유 append 잠금, projection 잠금을 확보하고,
  실행 중인 다른 프로세스가 대상 파일을 열고 있지 않은지 확인한다.
- 원본 **전체 바이트**와 대상 작업의 조회 DB 행들을 먼저 백업한다. DB의 후반 기록이
  파일보다 더 남아 있을 수 있으므로 원본만 백업해서는 안 된다.
- 온전히 저장된 줄은 바이트 단위로 보존한다. 해당 작업의 파생 조회 행만 비우며
  다른 작업의 행과 `state_5.sqlite`는 수정하지 않는다.
- DB 반영 중 실패하면 원본 바이트를 복원한다. 여러 DB 중 일부만 커밋됐다면
  그 DB는 다음 조회 때 재구축해야 할 수 있다. 백업과 `repair.json`을 함께 보존한다.

백업은 관리 루트의 `history-recovery/crash-<시각>-<식별자>/` 아래에 생긴다.
`original.jsonl`, `index-N.sqlite`, `repair.json`을 함께 보관한다. 폴더는 사용자 전용
권한(0700)이며 대화 본문을 포함하므로 Git이나 공개 진단 자료에 넣지 않는다.
화면에 없는 마지막 기록은 백업에서 별도 조사할 수 있지만, 불완전한 내용을 추측해
대화에 추가하거나 이미 실행했을지 모르는 명령을 자동 재실행하지 않는다.

## 복구 뒤 검증

1. 같은 프로필의 실제 SSH 경로로 `thread/read`와 `thread/resume`이 성공하는지 확인한다.
   새 모델 답변을 시작할 필요는 없다.
2. 원본의 보존 구간이 백업의 같은 구간과 정확히 일치하는지 확인한다.
3. 재생성된 `thread_history_projection_state`가 완전한 파일 길이·ordinal과 맞는지 확인한다.
4. UI에서 다른 작업을 선택했다가 대상 작업을 다시 연다. 강제 종료 전 마지막 명령의
   실제 실행 결과를 확인한 뒤 후속 개발을 진행한다.

전체 파일을 백업으로 되돌려야 한다면 먼저 해당 작업의 작성자·조회자를 멈추고 같은
잠금을 확보해야 한다. 복구 후 새로운 메시지가 생겼다면 백업으로 덮어쓰면 안 된다.
새 기록을 별도 보존하고 병합 범위를 검토한다. 백업 원본 자체에는 최초의 손상이
남아 있으므로 단순 원복이 재개 성공을 의미하지 않는다.

## 이번 확인 결과와 한계

- Linux 임시 저장소 시험 9개 통과: 원본·다른 작업 보존, 백업, 중간 손상 거부,
  포크 보호, 작성 잠금 충돌, 프로세스 확인 실패, DB 커밋 실패 시 원본 복원 포함.
- Windows에서는 읽기·검사 시험 5개 통과, Linux 적용 시험 4개 제외.
- 실제 대상 작업의 8,146개 완전한 줄을 그대로 보존했다. 1,436바이트의 불완전한
  마지막 부분과 조회 DB의 후반 기록은 백업에 보관했다.
- 실제 관리 SSH 연결로 읽기·재개 성공, 조회 체크포인트와 파일 길이 일치,
  원본 SHA-256 및 보존 구간 일치, 파일 소유자 유지까지 확인했다.
- 별도 웹 연결은 Windows에서 HTTP 200을 확인했다. 사용자의 브라우저 화면 조작,
  복구 후 새 모델 답변 생성, 향후 강제 전원 차단 상황은 이번 검증에 포함하지 않는다.
- 이 도구는 손상 복구 수단이다. 런타임의 디스크 영속화 순서를 변경한 것은 아니며,
  갑작스러운 전원 차단에 의한 미저장 기록 손실을 방지한다고 보장하지 않는다.
